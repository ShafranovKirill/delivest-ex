# Рефакторинг экспорта и импорта слепка всей франшизы

Исходные требования описаны в [задаче по слепку сайта](site-snapshot.md#5-слепок-всей-франшизы). Базовая реализация находится в серверном коммите `5e7e000`. Экспорт уже собирает все филиалы без `deleted_at`, включая неактивные, а импорт работает под глобальной блокировкой. После исправлений архив должен повторно импортироваться целиком даже при общем каталоге и переносить каждый выбранный раздел независимо.

## 1. Разделить подготовку и применение слепка

- Сохранить публичные функции `Delivest.SiteSnapshot` и существующие точки входа админки. Оставить в контексте проверку прав, оркестрацию операции и аудит. Выделить из него обработку ZIP и манифеста, чтение данных, построение плана импорта и его применение. Использовать существующие Ecto changesets, контексты и клиент S3. Разделять по ответственности по мере исправления сценариев ниже.
- Сохранить форматы `branch` и `franchise`, проверку идентификатора сборки, лимиты и правила проверки архива. Слепок филиала без поля `scope` продолжает читаться по правилам исходной задачи. Проверить, что архив каждого типа отклоняется в точке входа другого типа.
- Построить единый план импорта франшизы. В плане должны быть целевые филиалы, соответствия сущностей, связи, ссылки на медиа и перечень действий после коммита. До записи в S3 проверить схему, уникальность записей, ссылки, права и конфликты сопоставления. Выполнить проверки состояния БД и применение плана под существующей глобальной блокировкой. После обращения к S3 повторно проверить ограничения, которые могли измениться из-за обычных действий в админке.
- Вынести общий перечень переносимых полей для каждого раздела. Использовать его при выгрузке, валидации и записи, чтобы эти три этапа принимали один и тот же набор данных.

## 2. Сопоставить филиалы и общий каталог на уровне всей франшизы

- Разрешать целевой филиал по паре «исходная установка и исходный ID», затем по `slug`. Восстанавливать мягко удалённый филиал, обновлять совпавший и создавать отсутствующий со свободным кодом. Отклонять неоднозначное сопоставление и ситуацию, когда две записи одного архива разрешились в один целевой филиал. Сохранять данные филиалов вне архива.
- Уточнить хранение соответствий филиалов. Сейчас импорт из другой установки может перезаписать соответствие для того же целевого филиала. Обеспечить независимые соответствия для разных исходных установок и однозначное разрешение каждого исходного ID. При изменении индексов сохранить действующие соответствия и покрыть миграцию тестом. Проверить также удаление целевого филиала с каскадным удалением соответствий и последующее сопоставление по `slug`.
- При чтении архива собрать каталог по типу сущности и исходному ID, а связи с филиалами собрать отдельно. Если один ID встречается в нескольких секциях, сверить переносимые поля. Разные данные под одним ID отклонять до загрузки файлов. Сформировать одно целевое соответствие для каждой общей сущности, включая категории, товары, группы, модификаторы, теги и медиа. Если старые соответствия для одного исходного объекта указывают на разные целевые записи, отклонить импорт с указанием сущности и филиалов.
- Проверять принадлежность каталога по множеству целевых филиалов слепка. Разрешить обновление общего объекта, если все затрагиваемые филиалы представлены в плане и архив задаёт для них согласованные данные. Отклонить изменение, если оно затрагивает каталог филиала вне архива. Зоны доставки проверять отдельно по владельцу. Зона одного филиала не может перезаписать зону другого.
- Записывать каждую общую сущность один раз в порядке зависимостей и отдельно создавать нужные связи с филиалами. Сохранять существующие записи и связи, отсутствующие в архиве. Повторный импорт должен использовать те же целевые ID. Считать уникальные записи отдельно от связей, чтобы общий товар не увеличивал число импортированных товаров дважды.

## 3. Сделать перенос интеграций независимым от бренда

- Перенести `yandex_org_id` и `yandex_api_key` из условного блока настроек бренда в данные общих интеграций. При импорте обновлять эти поля при выбранном разделе `integrations`, в том числе когда `franchise` отсутствует.
- Проверить матрицу разделов. Только `integrations` переносит общие и филиальные интеграции, сохраняя бренд и документы получателя. Только `franchise` переносит бренд, реквизиты, лояльность и документы, сохраняя интеграции получателя. При выборе обоих разделов применяются оба набора. Отсутствие записи в архиве сохраняет настройки получателя.
- Сверить разрешённые поля с исходной задачей и changesets интеграций. Проверить ЮKassa, Zvonok, DaData, Яндекс Еду и филиальные CRM, фискализацию, каналы и доставку. Для Яндекс Еды сохранить исключение `client_id` и `client_secret`. Сохранить предупреждение о секретах в админке. Ошибки, журналы и аудит не должны содержать значения ключей.

## 4. Привязать кэш и обработку медиа к результату транзакции

- Убрать очистку меню из `apply_franchise_data/4`. После успешного коммита очистить меню всех затронутых филиалов, кэш филиалов и франшизы, а при переносе интеграций обновить их кэш состояния. Проверить, есть ли у изменяемых глобальных справочников зависимые ключи меню вне списка импортированных филиалов. Ставить генерацию превью после коммита и один раз для каждой целевой записи медиа.
- Повторно использовать доступный S3-объект с тем же содержимым. Учитывать отдельно файлы, созданные текущей попыткой. При ошибке загрузки, записи или завершения транзакции удалить только эти файлы. Если очистка не удалась, записать ключи для повторной уборки. При ошибке импорта не запускать обработку превью и обновление кэшей.
- Сохранить серверную проверку администратора на обоих входах и глобальную блокировку импорта. Ожидаемые ошибки сопоставления возвращать как понятный отказ для админки с безопасным контекстом. Проверить, что при отказе по одному филиалу изменения остальных филиалов и служебных соответствий откатываются.

## Критерии приёмки

| Сценарий | Ожидаемый результат |
|---|---|
| Два филиала делят товар, категорию, модификаторы и фото. Экспорт, импорт в пустую БД и повтор того же импорта | Один экземпляр каждой общей записи, связи с обоими филиалами, стабильные ID и отсутствие новых записей и S3-объектов при повторе |
| После первого импорта изменены цена и фото общего товара | Повторный экспорт и импорт обновляют тот же целевой товар и витрины обоих филиалов |
| Целевой объект связан с филиалом вне архива, либо один исходный ID содержит разные данные | Понятный отказ по конфликтующему объекту. БД, связи, соответствия и S3 остаются в исходном состоянии |
| Существующий филиал, отсутствующий филиал, мягко удалённый филиал и филиал вне архива | Обновление, создание, восстановление и сохранение соответственно. Занятый код заменяется свободным, конфликт имени или ссылки откатывает импорт |
| Архивы двух установок сопоставлены одному целевому филиалу по `slug`, затем повторно загружен первый архив после изменения исходного `slug` | Сохранённое соответствие первой установки находит прежний целевой филиал |
| Выбран только раздел интеграций, только раздел франшизы или оба | Каждый раздел обновляет свои поля. В архиве без интеграций отсутствуют их ключи, а секреты не выводятся в диагностике |
| Меню было в кэше до импорта, витрина читает его во время импорта | После коммита запрос получает новый каталог. После отката витрина продолжает отдавать прежние данные |
| Сбой S3 после загрузки первого файла, ошибка БД после загрузки либо два одновременных импорта | При сбое нет частично применённых данных и удаляются только новые файлы. Параллельные импорты сериализуются без дублей |
| Архив повреждён, не совпадает сборка, подменён тип архива или у сотрудника нет прав | Сервер отклоняет операцию до записи. Раздел франшизы скрыт для сотрудника без прав администратора |
| Экспорт и импорт одного филиала | Существующие права, совместимость архива и ограничения на общие записи сохранены |

## Проверка перед сдачей

- Добавить регрессионные тесты в `test/delivest/site_snapshot_franchise_test.exs` или в тесты выделенных модулей. Проверять результаты через публичные функции импорта и экспорта. Для S3 проверить количество объектов, переиспользование и уборку при ошибке. Для админки проверить права на скачивание, импорт и предупреждение о секретах.
- Запустить целевые тесты слепка филиала, франшизы и `FranchiseLive`, затем выполнить `mix precommit` согласно требованиям серверного проекта.
- Пройти полный цикл на двух тестовых инстансах одной сборки с разными БД и S3-бакетами. Проверить витрины двух филиалов, цены, фото, юридические документы и выбор разделов. Повторить импорт и зафиксировать числа записей и файлов до и после.
