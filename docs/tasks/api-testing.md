# Практическая проверка внешних API

Список того, что нельзя узнать из документации и заглушек и нужно проверить руками на тестовых средах. Результаты закрепляются в контрактных тестах и в README интеграций, после чего пункты соответствующих задач можно закрывать.

Задачи, к которым относятся проверки: [frontpad.md](frontpad.md), [iiko-api.md](iiko-api.md), [rkeeper-api.md](rkeeper-api.md), [yandex-eda-api.md](yandex-eda-api.md), [yandex-delivery-api.md](yandex-delivery-api.md), [atol-api.md](atol-api.md), [yookassa.md](yookassa.md), [small-integrations.md](small-integrations.md), [otp-usage.md](otp-usage.md).

## Как проверять

- Запросы делать из приложения (чтобы они попали в журнал интеграции, `/staff/integrations/<провайдер>`, и были видны сырые тело и ответ) или через `curl` и Postman. Если из приложения, `Journal` сохраняет запрос и ответ с маской секретов.
- Каждый ответ, который меняет поведение кода, сохранять как образец: `test/support/fixtures/<провайдер>/<случай>.json`. Из образцов потом делаются заглушки `Req.Test` и контрактные тесты (`--only iiko_contract`, `--only rkeeper_contract`, `--only atol_contract`, `make contract P=yandex_eda`).
- Для каждого пункта записывать три вещи: что отправили, что ответили (код, тело), сколько заняло. Если ответ расходится с ожиданием, в первую очередь дописать это в README интеграции и в соответствующую задачу.
- Чеклист: отметить `[x]` и дописать результат одной строкой справа.
- Безопасность: только тестовые аккаунты и заведомо тестовые телефоны. Любой заказ, курьер, платёж или чек, созданный на боевом контуре (Яндекс Доставка, АТОЛ), сразу отменять или сторнировать. Боевые ключи не вставлять в тестовые настройки.
