## 1. credo и dialyxir

В `mix.exs` нет ни `credo`, ни `dialyxir`. В `ci.yml` есть шаг кэша PLT для dialyzer, но самого запуска нет: шаги — формат, компиляция с `--warnings-as-errors`, тесты. В [бэклоге](backlog.md) пункт 1 говорит «прогнать credo и dialyzer», запускать пока нечем. `@spec` стоит в 147 местах на 563 модуля.

- Добавить `{:credo, "~> 1.7", only: [:dev, :test], runtime: false}` и `{:dialyxir, "~> 1.4", only: [:dev, :test], runtime: false}`.
- `.credo.exs` в строгом режиме без правил про комментарии и `@moduledoc`: в проекте их не пишем.
- Шаги `mix credo --strict` и `mix dialyzer` в `ci.yml` после компиляции, PLT уже кэшируется.
- Исправить найденное. Если находок много, `.dialyzer_ignore.exs` с причиной на каждую строку, а не молчаливый список.
- Добавить `credo` в алиас `precommit`.

Делается первым: все следующие изменения идут уже под проверкой типов.

## 2. Задача без супервизора в вебхуке iiko

`integrations/iiko/webhook.ex:35`:

```elixir
defp accept(info, %{"eventType" => "StopListUpdate"}) do
  Task.start(fn -> StopSync.sync(info.branch_id) end)
end
```

Это единственный `Task.start` в проекте. Задача не под супервизором и без повторов: упадёт на ошибке iiko, и стопы не обновятся до опроса раз в 10 минут. Пачка вебхуков подряд запускает столько же параллельных синхронизаций.

Второе похожее место: `YandexEda.StopList.refresh/1` запускает `Task.async` (связанный процесс) на каждый заказ Яндекса, исключение синхронизации убивает запрос, см. [yandex-eda-api.md](yandex-eda-api.md) п.1.

Решение: `Poller.enqueue(Crm.StopPoller, info.branch_id)`. У `Poller.Worker` уже есть уникальность по `[:poller, :target]` в состояниях `available` и `scheduled`, так что повторные вебхуки схлопываются, а ошибка идёт в повторы Oban. Остальные входящие события iiko уже идут через `Inbox.accept`, этот единственный обходил надёжный путь.

## 3. Одновременный выпуск токена

`integrations/token_cache.ex`: `fetch/2` делает `Cachex.get`, при промахе `refresh`, который сначала удаляет ключ, потом зовёт `issue.()`. Два одновременных запроса к одному аккаунту оба видят промах и оба выпускают токен.

Что известно по провайдерам:

- **iiko.** Токен — JWT на 1 час, обновления по refresh-токену нет (описание `access_token` в `iiko/docs/openapi.json`). Про то, что новый токен гасит прежний, ничего не сказано, JWT обычно без состояния. Худший случай — лишний запрос выпуска.
- **r_keeper.** Токена с жизненным циклом нет: статический ключ UCS из конфига (`rkeeper/api.ex:58`), `TokenCache` не используется.
- **Яндекс Еда.** Токен через `TokenCache` (push API), условия те же, что у iiko.

Решение: баг не срочный, но чинится дёшево и без риска. Выпускать через `Cachex.fetch/4`: Cachex сериализует вызовы по ключу, второй вызов ждёт результат первого. TTL из ответа провайдера передаётся как `{:commit, token, expire: ...}`, ошибка выпуска как `{:ignore, error}`, чтобы она не кэшировалась. Принудительное обновление после 401 остаётся отдельным путём: удалить ключ, потом `fetch`.

Тест на конкурентный выпуск: 20 параллельных вызовов, выпуск ровно один.

## 4. Throttle CRM занимает слот очереди

`integrations/crm/throttle.ex` вычисляет слот и спит `Process.sleep(slot - now)` внутри задачи Oban. Очередь `:crm` берёт 2 задачи (`config/config.exs:13`), у Frontpad интервал 2 секунды (`frontpad.ex:112`). Две задачи одного аккаунта в очереди на отправку держат оба слота, заказы остальных филиалов ждут. Это уже записано в `integrations/README.md` как ограничение.

Решение без `sleep`: `Throttle.run/2` возвращает `{:error, {:throttled, ms}}`, когда слот ещё не наступил, и не резервирует его. `Crm.classify_error/2` превращает это в `{:snooze, секунды}`, `SyncWorker` и `CommandWorker` уже умеют отдавать `{:snooze, seconds}` (`sync_worker.ex`, `command_worker.ex`). Слот резервируется только в момент реального вызова.

- Обновить раздел «Ограничения» в `integrations/README.md`.
- Тест: два заказа одного ключа, второй получает snooze, а не ждёт; заказ другого ключа проходит сразу.

## 5. HTTP-клиент: повторы и лежащий провайдер

`HTTP/client.ex` вызывает `Req.request/1` с настройками из конфига. В тестах стоит `retry: false` (`config/test.exs:8`), в проде не задано, то есть действует поведение Req 0.7.3 по умолчанию (`deps/req/lib/req/steps.ex`): `:safe_transient`, повторы только для GET и HEAD при временных ошибках и ответах 408, 429, 500, 502, 503, 504, до трёх раз с растущей паузой. POST не повторяется.

Что это значит для нас:

- Почти все вызовы CRM (iiko, r_keeper, Frontpad) и АТОЛ регистрация идут POST, скрытых повторов у них нет. Повторы делает Oban.
- GET-запросы повторяются внутри одной попытки Oban: `Zvonok` подтверждение номера (`phones/confirm` — GET, каждый вызов расходует кампанию), `YandexDelivery.tracking-links`, `AtolOnline.report`. Повтор не виден в журнале интеграций (`Journal.outgoing` пишет итог) и не учитывается `Throttle`.

Решение:

- `Zvonok.Api.confirm/2`: `retry: false`, повторять вход должен клиент или лимит из [small-integrations.md](small-integrations.md), а не транспорт.
- Остальные GET остаются с повторами: они безопасные.
- В `HTTP.Client` принять опцию `retry:` для вызова, по умолчанию как сейчас.
- Лёгкая защита от лежащего провайдера без новой зависимости: таблица `integration_health` уже хранит `:failed` и `:auth` (`Integrations.Health`). Воркер перед вызовом смотрит статус аккаунта, при `:failed` свежее минуты отдаёт `{:snooze, 60}`, не долбит мёртвый API. Любой успешный вызов уже зовёт `Health.recovered`.
- Не вводить `fuse` или аналог, пока статуса из `Health` достаточно.
- Тест: GET-запрос Zvonok при 502 уходит один раз.

## 7. Отправка на кухню по времени

`Kitchen.dispatch_due/1` (`oms/kitchen.ex:68`) раз в минуту (`config/config.exs:22`) делает `Repo.all` по всем заказам `:accepted` с join на `branch_info` и фильтрует по `cook_by - lead_minutes <= now`. Заказ с будущим `cook_by` уходит на кухню с задержкой до 60 секунд, запрос выполняется каждую минуту всегда.

Образец уже есть: `Kitchen.ReadyWorker` с `schedule_in` и `unique: [keys: [:order_id]]`. Сделать так же:

- `Kitchen.SendWorker`: `scheduled_at: sends_at(order, kitchen)`, уникальность по `order_id`, внутри проверка, что заказ всё ещё `:accepted` и срок пришёл.
- `Kitchen.order_accepted/1`: если срок не пришёл, ставит задачу, а не ждёт сканирования.
- Переносы: изменение `cook_by` (событие `order.updated`, поле уже в `order_events.ex:14`) пересоздаёт задачу; уход из `:accepted` (отмена, откат, CRM) отменяет её. `Kitchen.OrderSubscriber.events/0` расширить на `order.updated`.
- Изменение `lead_minutes` или включение кухни в настройках филиала перепланирует заказы этого филиала в `:accepted`.
- `DispatchWorker` остаётся страховкой, но раз в 5 минут: подбирает то, что не успело или потерялось. Он же покрывает рассинхрон при ручных правках в базе.
- Тесты: заказ с `cook_by` через 30 минут получает задачу на нужный момент; перенос времени сдвигает её; отмена убирает; страховочный проход подбирает заказ без задачи.

Выигрыш честно скромный: точность до секунды и один запрос в 5 минут вместо каждой минуты. Остальное сделано правильно и менять не нужно (см. ниже).

## 8. Одна нода

Решение: приложение работает на одной ноде, масштабируется вверх. Кэши Cachex, счётчики `rate_limit_cache`, ETS `:kitchen_last_seen` остаются локальными, это корректно для одной ноды. Нагрузки одной ноды с запасом хватает; деплой без простоя решается на уровне nginx, а не кластером.

Но код и зависимости сейчас выглядят рассчитанными на кластер, и это вводит в заблуждение:

- Убрать `{DNSCluster, ...}` из `application.ex:16`, `config :delivest, :dns_cluster_query` из `config/runtime.exs:104` и зависимость `dns_cluster` из `mix.exs:69`.
- Записать в `DEPLOY.md`: нода одна, `RELEASE_NODE` и `DNS_CLUSTER_QUERY` не нужны. Если появится вторая нода, до запуска нужно сделать три вещи: рассылку инвалидации кэшей по PubSub (в `lib` 18 файлов с `Cachex.del/clear`), общий счётчик для `RateLimit` и `Crm.Throttle`, хранение `kitchen_last_seen` в базе. Какие кэши и с каким сроком устареют, перечислено ниже.

Что устарело бы на второй ноде (для справки при будущем решении):

| Кэш | TTL | Последствие |
|---|---|---|
| `staff_cache` | 5 минут | Отозванное право или удалённый сотрудник работает до 5 минут (`identity/staffs.ex:232`) |
| `menu_cache`, `stock_cache` | 1 час | Новая цена, скрытый товар или акция видны через час (`net/catalogs.ex:6`, `net/stocks.ex:34`) |
| `branch_cache` | 1 час, слаг 24 часа | Смена настроек филиала, зоны, расписания |
| `stop_cache` | 60 секунд | Стоп, снятый на одной ноде, держится на другой до минуты (`net/stops.ex:9`) |
| `franchise_cache` | без срока | Смена настроек франшизы не дойдёт до другой ноды до её перезапуска (`franchise/settings_store.ex:10`) |
| `promo_cache`, `cart_cache` | | Устаревшие акции в корзине |

## 9. Импорт меню

`Net.MenuImport.apply/4` (`net/menu_import.ex:44`) в одной транзакции для каждого товара вызывает `upsert_product`, потом для каждой группы `upsert_group`, внутри для каждого модификатора отдельный upsert (`:169`). На меню в тысячу позиций это тысячи запросов в одной транзакции, во время которой держатся блокировки.

Сначала замерить: прогнать импорт на меню r_keeper и iiko из тестовых данных, посчитать запросы и время. Если меньше секунды, оставить как есть. Если нет: `Repo.insert_all` с `on_conflict` пачками по 500, внешние id и ссылки на группы собирать в памяти. `Task.async_stream` здесь не нужен: узкое место база, а не вычисления.

## Что проверено и менять не нужно

- **Поллеры.** Не сканирование: `Poller.Worker` сам себя планирует через `schedule_in`, а cron раз в минуту только раскладывает цели (`enqueue_all`). Уникальность по `[:poller, :target]` не даёт копиться.
- **Отложенное `ready` на кухне.** `ReadyWorker` с `schedule_in` и отменой через `Oban.cancel_all_jobs` — правильный образец, на нём строится п.7.
- **Закрытие вчерашних заказов.** `StaleOrderWorker` раз в час: суточная уборка по расписанию, процесс на каждый заказ не нужен.
- **Outbox.** Транзакционная запись события и задачи подписчику (`Events.record/5` вместе с `Ecto.Multi`, `DeliverWorker` с уникальностью `[:event_id, :subscriber]`). Образцовая реализация.
- **Состояние в процессах.** Состояние заказов, корзин и интеграций должно жить в Postgres и переживать перезапуск. GenServer на домен не нужен. Единственный GenServer, `Logs.Buffer`, на своём месте: пакетная запись логов с ограничением `@max_pending`.
- **Параллельные потоки.** `Task.async_stream` и `GenStage` не нужны: внешние вызовы идут через Oban, узкие места в базе и в лимитах провайдеров.
- **Presence и PubSub.** Используются правильно, кухня, курьеры и клиентский канал на одних и тех же темах.
