# Задача: обновление сайта при ограничении Docker Hub

Статус: к реализации. Репозитории: корневой Delivest, `agent/`, при изменении экрана обновления соседний `delivest-bastion`. Это узкое исправление конкретного сбоя в рамках [надёжности развёртывания](deployment-reliability.md).

## Цель и воспроизведение

Bastion сообщает об ошибке обновления после успешного бэкапа и `git pull`: `docker compose pull` запрашивает `nginx:1.28-alpine` и получает HTTP 429 от `registry-1.docker.io`. Compose отменяет загрузку остальных образов. Задача выполнена, когда временное ограничение Docker Hub при наличии нужных локальных инфраструктурных образов не мешает доставить новую версию Delivest и ошибка отсутствующего образа не меняет работающий сайт.

Точки входа: `agent/lib/delivest_agent/commands.ex` (`execute("update", ...)`), `agent/lib/delivest_agent/compose.ex`, `agent/lib/delivest_agent/release.ex`, корневой `docker-compose.yml`. Сейчас `Compose.pull/2` получает все сервисы, кроме агента. `gateway` использует `nginx:1.28-alpine`, `postgres` использует `postgres:16-alpine`, `s3` использует `chrislusf/seaweedfs` без тега. Последний фактически равен изменяемому `latest`. `server` и `client` используют GHCR с изменяемым тегом `latest`.

## Границы и решение

1. Сначала закрепить фактически используемый и проверенный образ `s3` конкретным тегом или digest. Для `gateway` и `postgres` желательно закрепить digest проверенного образа, поскольку их текущие теги тоже могут быть перезаписаны. Проверить совместимость нового reference с установленными контейнерами и данными. До закрепления никакой пропуск pull по локальному `chrislusf/seaweedfs` без тега не допускается. Общее правило пропуска по кэшу применять только к закреплённому digest или проверенному неизменяемому тегу, никогда к отсутствующему тегу или `latest`.
2. Разделить сервисы по назначению на основе текущего compose и списка реально запущенных сервисов. Образы приложения `server` и `client` обязательно запрашивать из GHCR для целевого выпуска. Локальный образ с тем же изменяемым тегом `latest` не доказывает, что это целевой выпуск. Для закреплённых инфраструктурных `gateway`, `postgres`, `s3` проверять наличие точного reference локально. Если образ есть, не выполнять для него лишний сетевой pull. Если образа нет или ссылка изменилась, скачивать его до изменения работающих контейнеров.
3. Для сетевого сбоя 429 у требуемого образа добавить ограниченные повторы с возрастающей паузой. Повторять только скачивание, а не весь сценарий с новым бэкапом. Ошибку и число попыток показывать в журнале Bastion. Не выполнять бесконечные повторы.
4. При неуспехе обязательного pull завершать обновление с ошибкой до `docker compose up` и рестарта gateway. Не выдавать локальный устаревший образ приложения за успешное обновление. Проверить, что последующий `docker compose up` не делает скрытый pull пропущенного сервиса из-за `pull_policy` или поведения Compose. При необходимости явно задать безопасную политику запуска после подготовленных pull. Сохранить текущий порядок бэкапа, запоминания запущенных образов, проверки здоровья и отката после неудачного запуска.
5. Покрыть разбор состава сервисов и ошибки с помощью существующих fake runner тестов `agent/test/delivest_agent/commands_test.exs`. Убедиться, что для отсутствующего локального `nginx:1.28-alpine` всё же выполняется pull и ошибка блокирует запуск. Не привязывать решение к одному имени образа, так как версии compose могут измениться.
6. В журнале обновления различать пропущенный pull уже имеющегося закреплённого образа, скачивание приложения и исчерпание повторов. Описать оператору повтор команды после восстановления доступа к registry в `DEPLOY.md`.

## Приёмка и проверка

- При локально доступных закреплённых инфраструктурных образах и 429 на Docker Hub агент не обращается к нему для этих сервисов, скачивает целевые образы Delivest и запускает обычные проверки здоровья.
- При отсутствии необходимого инфраструктурного образа и исчерпании повторов работающие контейнеры остаются запущенными. Журнал называет сервис, registry и причину.
- Ошибка загрузки `server` или `client` не приводит к `up` и не выдаёт успех по локальному `latest`.
- Обновление после изменения версии инфраструктурного образа действительно получает новую версию.
- Проверить тестами агента оба пути и `mix test` в `agent/`. Проверить `docker compose config` с действующим compose. Развёртывание production, push и релиз в эту задачу не входят.

Более широкий переход на согласованные release digest и управление состояниями раскатки остаётся в [deployment-reliability.md](deployment-reliability.md).
