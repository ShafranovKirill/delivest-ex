# Задача: строгие статусы заказа и модуль доставки

Статус заказа становится конечным автоматом: только вперёд, у каждого перехода есть исполнитель. Поверх него — модуль доставки: поиск курьера среди своих курьеров или в Яндекс Доставке, отдельная роль курьера со своей страницей.

## Решения

| Вопрос | Решение |
|---|---|
| Откат статуса | Нельзя. Только администратор с правом `orders.revert`, причина обязательна, пишется в аудит |
| Пропуск этапа | Людям нельзя, только на следующий этап. CRM может перескочить — недостающие переходы дописываются с источником `crm` |
| Отмена | Оператор и канал (Яндекс Еда). Отмену каналом оператор видит тревогой и подтверждает, что ознакомился |
| Кто вёл заказ | Каждый переход хранит исполнителя: оператор принял, повар готовил, курьер вёз |
| Филиал на Frontpad | Доставку ведёт Frontpad (у него своя интеграция с Яндекс Доставкой). Наш поиск курьера не запускается |
| Источник курьеров | В настройках филиала: свои курьеры или Яндекс Доставка |
| Наличные и Яндекс | Курьер Яндекса берёт оплату только картой. При вызове Яндекса заказ за наличные переводится на «Картой курьеру» (`card_offline`), это пишется в историю заказа |
| Свои курьеры | Заявку видят все курьеры филиала. Взял один — у остальных она пропадает |
| Отказ курьера | До «Забрал», без причины. Заказ снова уходит в поиск |
| Назначение курьера | Администратор и оператор могут назначить курьера на заказ сами, минуя поиск, и снять его до «Забрал» |
| Несколько заказов | Курьер может взять несколько |
| Вручение | Курьер отмечает «Вручил» — заказ завершён. Для наличных и терминала этим же подтверждает получение оплаты |
| Когда искать курьера | Настройка филиала: «Вручную» / «Когда начали готовить» (по умолчанию) / «Когда готов». Кнопка «Найти курьера» у оператора есть всегда |
| Карта у курьера | MapLibre с двумя точками: филиал и клиент. Маршрут не строим. Кнопки «Яндекс Навигатор» и «Яндекс Карты» открывают маршрут в приложении. Нет координат у адреса — адрес словами и поиск по тексту |

## Автомат заказа

`created → accepted → preparing → ready → delivering → completed`, из любого незавершённого — `cancelled`.

| Переход | Кто |
|---|---|
| `created → accepted` | оператор, канал (автоподтверждение), CRM |
| `accepted → preparing` | повар, оператор, CRM |
| `preparing → ready` | повар, оператор, CRM |
| `ready → delivering` | доставка («Забрал» курьера, Яндекс), оператор |
| `delivering → completed` | доставка («Вручил» курьера, Яндекс), оператор |
| `ready → completed` | оператор — самовывоз и зал |
| `* → cancelled` | оператор, канал |
| на шаг назад | `orders.revert` с причиной |

Статус меняется только через автомат. Прямая запись `status` в changeset убирается.

Откат снимает последний переход: статус возвращается к его `from`, в том числе из `completed` и `cancelled`.

Источник `system` (закрытие заказов прошлых дней, `StaleOrderWorker`) может перескакивать этапы, как CRM.

### Настоящий статус в `orders.status`

Сейчас у заказа, переданного в CRM, в базе лежит псевдостатус `crm`, а настоящий вычисляется при чтении из `crm.remote_status` и `channel.remote_status` — в Elixir (`OrderStatus.current/1`) и в SQL (`OrderScopes.effective_status/0`), и они расходятся: SQL не учитывает канал.

- Псевдостатус `crm` убирается. Статусы CRM и канала проходят через автомат и пишутся в `orders.status`.
- Миграция заполняет `status` у существующих заказов из `crm` и `channel`.
- Запрет редактировать заказ, переданный в CRM, берётся из наличия `crm`, а не из статуса.
- `effective_status` и вычисление в `OrderStatus.current/1` убираются, везде читается `orders.status`.

### Админка

- Выпадающий список статусов убирается.
- Кнопка следующего шага, её видит тот, у кого есть право на этот переход: повар — кухня, оператор — всё.
- «Отменить» — с причиной, как сейчас.
- «Откатить» — только с `orders.revert`, окно с обязательной причиной.
- Блок «Кто вёл заказ» из `order_transitions`.
- Пресет роли «Повар» с `orders.cook`.

Каждый переход — строка в `order_transitions`: заказ, из, в, источник (`staff`, `crm`, `channel`, `courier`, `system`), сотрудник, причина, время. Из неё карточка заказа показывает, кто вёл каждый этап.

## Кухня

| Вопрос | Решение |
|---|---|
| Включение | Галочка «Кухня работает» в настройках филиала. Выключена или филиал на Frontpad — экрана нет и автоперехода в `preparing` нет: «Начать готовить» и «Готов» ставит оператор |
| Роль | «Кухня» с правом `orders.cook`. Планшет общий, в журнал пишется аккаунт кухни, конкретный повар не важен. Кухня одна, цехов нет |
| Что видит кухня | Только заказы в `preparing`. Отмечает «Готово» — заказ уходит в `ready` и пропадает с экрана |
| Когда заказ попадает на кухню | Переход `accepted → preparing` делает система, когда до `cook_by` осталось N минут (настройка филиала, по умолчанию 90). Заказ «на сейчас» уходит на кухню сразу после подтверждения |
| Раньше срока | У оператора кнопка «Передать на кухню» на подтверждённых заказах, которые ещё не на кухне |
| Готовность | Только заказ целиком |
| Стоп-лист с кухни | Нет, повар договаривается с оператором |
| Комментарий | Один на заказ, без разделения |
| Печать | Нет, только экран |

### Экран кухни

- Отдельный адрес `/staff/b/:slug/kitchen`, без меню и шапки админки. Кнопка «Во весь экран» (Fullscreen API) и запрет гаснуть экрану (Wake Lock). Это же нажатие разрешает браузеру звук.
- Карточка: номер, тип (доставка, самовывоз, зал), **к какому времени** и **сколько уже готовится** — крупно сверху. Ниже позиции крупным шрифтом с количеством, подарки отмечены, комментарий заказа. Кнопка «Готово» на всю ширину.
- Порядок: самые срочные первыми. После `cook_by` карточка краснеет.
- Новый заказ — звук и подсветка карточки.
- «Готово» — карточка показывает «Готово ✓» и 10 секунд кнопку «Вернуть». Переход в `ready` выполняется только по истечении 10 секунд (отложенная задача Oban, «Вернуть» её снимает), поэтому статус назад не ходит.
- Потеря связи — на весь экран красная плашка «Нет связи — новые заказы не придут», пока LiveView не переподключится.
- Сессия аккаунта кухни бессрочная, планшет не разлогинивается: аккаунту с `orders.cook` без `orders.update` при входе ставится подписанная cookie на год, по ней сессия восстанавливается. Такой аккаунт после входа попадает сразу на экран кухни.
- Сбоку компактный список «Скоро на кухню»: подтверждённые заказы ко времени, которые придут в ближайший час, — номер и время. Кнопок у них нет.

### Контроль оператора

- Индикатор «Кухня на связи / нет связи N минут» в шапке админки по Phoenix Presence экрана кухни.
- Заказ стал готов — уведомление со звуком «Заказ №… готов».
- В карточке заказа в `preparing` — сколько он на кухне. Просрочен `cook_by`, а готовности нет — тревога оператору.

## Попытка доставки

Отдельная таблица `deliveries`: одна запись — одна попытка доставить заказ.

`searching → assigned → picked_up → delivered`, выход `cancelled` / `failed`.

- Отказ курьера, «курьер не найден» у Яндекса — попытка закрывается, создаётся новая в `searching`. Заказ назад не идёт.
- Отмена заказа отменяет активную попытку (у Яндекса — `claims/cancel`).
- `picked_up` двигает заказ в `delivering`, `delivered` — в `completed`.
- Провайдер — behaviour с реестром по образцу `Crm.Provider`: `:staff` (свои курьеры), `:yandex` ([integrations/yandex_delivery](../../lib/delivest/integrations/yandex_delivery/README.md)).
- Запуск поиска — по событию перехода заказа, неважно, сделал его повар или CRM.

## Роль курьера

- Права: `orders.cook` (переходы кухни), `orders.deliver` (страница доставки), `orders.revert`. Роли собираются из прав.
- Страница «Доставка» в админке, удобная с телефона, обновляется через PubSub.
- Курьер видит: филиал и адрес забора; адрес клиента с подъездом, этажом, квартирой, домофоном, комментарием; имя и телефон клиента; сумму к получению и способ оплаты.
- Курьер не видит: цены позиций, скидки, акции, чужие заказы.
- Кнопки: «Взять», «Отказаться» (до «Забрал»), «Забрал», «Вручил», «Открыть в навигаторе».
- Оператор в карточке заказа выбирает курьера из курьеров филиала: попытка сразу становится `assigned`, курьер видит заказ у себя. Снять или заменить — до «Забрал».

## Каналы

- Яндекс Еда, схема `yandex` — курьер Еды, наш поиск не запускается.
- Яндекс Еда, схема `marketplace` — в наш модуль доставки, как заказ из приложения.
- Яндекс Еда, схема `pickup` и самовывоз — без доставки.

## Этапы

1. Настоящий статус в `orders.status` без псевдостатуса `crm`, автомат заказа, `order_transitions`, права и пресет «Повар», перевод всех мест смены статуса на автомат (админка, Frontpad, Яндекс Еда, `StaleOrderWorker`), тревога об отмене каналом, откат с причиной, кнопки в карточке заказа.
2. Кухня: настройки филиала («Кухня работает», за сколько минут на кухню), автоматический переход в `preparing`, кнопка «Передать на кухню», экран кухни, контроль оператора.
3. `deliveries`, провайдер `:staff`, настройки филиала (источник, режим поиска), кнопка «Найти курьера», страница курьера.
4. Провайдер `:yandex`: заявка, подтверждение, опрос журнала, данные курьера, ссылка отслеживания.
5. Админка как PWA: манифест, установка на телефон и планшет, service worker. Web Push сотрудникам: курьерам — новая заявка, оператору — новый заказ, отмена каналом, заказ готов. Инфраструктура пушей та же, что у клиентского приложения (`Delivest.Push`).
   Геопозиция курьера: пока открыта страница «Доставка», телефон раз в 20 секунд (если сдвинулся на 30 м) отправляет точку по сокету LiveView. Последняя точка хранится в Presence курьера, в базу не пишется. Оператор видит курьера на карте в карточке заказа в доставке с «обновлено N мин назад» и страницу «Курьеры» с картой филиала: все курьеры на связи и их заказы. В фоне и с заблокированным экраном браузер позицию не отдаёт — это ограничение платформы.
