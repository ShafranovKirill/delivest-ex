# Задача: отладить сборку, развёртывание и управление установками

Статус: частично сделано (2026-11-04). Готовность отделена от «хост ответил»: см. п. 3. Остальные пункты — к реализации. Репозитории: корневой Delivest, агент в `agent/`, соседний `delivest-bastion`.

Цель: предсказуемое обновление и восстановление после ошибок при сохранении текущего Docker Compose и Bastion. Без перехода на Kubernetes и без отдельной платформы развёртывания.

## Ограничения

- Образы поставляются из GHCR. Не предполагать наличие старых релизов без проверки реестра и правил очистки.
- Текущий `.github/workflows/release.yml` описывает публикацию `X.Y.Z`, `X.Y` и `latest`; это описание CI, а не доказательство сохранности образов в GHCR.
- Бэкапы фотографий/других загруженных файлов не добавлять. Остаётся существующий бэкап базы.
- Bastion обслуживает установки, а приложение продолжает работу без него. Управление доступом франшиз описано отдельно в [задаче подписок](franchise-feature-access.md).

## 1. Проверить реальную цепочку сборки

- Проверить, какие workflow действительно запускаются на PR, merge и выпуске, и на какой ревизии submodules; исключить выпуск без обязательных проверок.
- Согласовать версии Elixir/Erlang между `.tool-versions`, Dockerfile, PR CI, release CI и E2E. Сейчас в корневых checks/release указаны Elixir 1.17.3 / OTP 27.3, а документация задачи CI описывает 1.19.5 / OTP 28.4.2. Установить фактический рабочий набор и использовать один источник версий, где возможно.
- Проверить, что сервер, клиент, агент, схема API и конфигурация запуска соответствуют одному выпуску. Не выпускать частично собранный релиз как готовый.
- Записывать версию и исходную ревизию в метаданные всех трёх образов; подтвердить, что агент и Bastion показывают фактически запущенные значения.
- Проверить GHCR: действующие теги, перезапись, retention/очистку, доступ production к pull и обработку ошибок авторизации. Итоги и воспроизводимые шаги занести в README/DEPLOY.

## 2. Согласованное обновление из GHCR

Минимальное требование: одна операция массового обновления не должна незаметно ставить разные сборки разным установкам.

- Если версионированные образы уже сохраняются, использовать их digest и точную ревизию конфигурации.
- Если в GHCR реально остаётся только последний образ, сначала поправить публикацию/retention: сохранять хотя бы текущий целевой выпуск и поддерживаемый предыдущий. Не добавлять неработающую кнопку выбора удалённых версий.
- `latest` можно оставить как указатель на новый выпуск. При начале раскатки разрешить его в конкретные digest и зафиксировать их для всех установок; новый push не меняет уже начатую операцию.
- Связать целевые образы и compose/gateway-конфигурацию в одно описание выпуска. Не совмещать произвольный текущий `git pull` с образами другой ревизии.
- До остановки/пересоздания работающих сервисов проверить наличие и скачать все целевые образы. Неуспешный pull должен оставлять работающую установку без изменений.
- Сохранить предыдущие локальные образы, конфигурацию и информацию отката. Не удалять их очисткой Docker, пока они нужны для возврата; учесть несколько установок на одном Docker-хосте, чтобы метки предыдущих образов не затирали друг друга.
- Сначала контрольная установка, затем существующая последовательная раскатка с остановкой на первой ошибке. Выбранный выпуск и результат каждого шага видны владельцу.

## 3. Готовность и откат

Сделано: `/health` (живость) и `/ready` (база и применённые миграции, `503` при неготовности) в `Delivest.Health` / `HealthController`; агент для домена `api` открывает `/ready` и требует `status: ok`, для сайта — маркер `<div id="app">`, а не просто код меньше 500; Bastion проверяет те же два документа снаружи. Осталось: версия целевого выпуска в проверке, проверка после отката и запрет автоматического отката при несовместимой схеме.

- Сейчас `DelivestAgent.Status` и `Bastion.Checks.External` считают HTTP `status < 500` успехом. Развести «хост отвечает» и «приложение готово»: ответ 404 сам по себе не доказывает успешное развёртывание.
- Использовать отдельный endpoint готовности: ожидаемый статус/тело, версия приложения, доступность БД и завершённость обязательной инициализации. Для клиентской витрины проверить ожидаемый документ/маркер и версию, а не только отсутствие 500.
- Обновление считается успешным, когда готов именно целевой выпуск. Сохранить проверку нескольких последовательных ответов и внешнюю проверку Bastion.
- Отдельно показывать исходную ошибку обновления и исход отката. Проверить готовность и после отката; не выдавать «Восстановлено» только по запуску команды compose.
- Автоматический откат образов не откатывает БД. Для обычных релизов использовать обратно совместимые миграции с разнесением добавления, перехода и удаления полей. Несовместимые изменения явно помечать в выпуске: автоматический откат к неподходящей версии запрещён.
- Существующий бэкап перед обновлением проверить: ошибка обязательного бэкапа должна останавливать изменение установки; для случаев, где бэкап сознательно недоступен, владелец видит это до запуска. Не считать пропущенный шаг успешно сделанным бэкапом.
- Проверить восстановление существующего дампа в отдельную временную БД и запуск приложения на восстановленной копии. Проверка распаковки через `pg_restore --file /dev/null` остаётся полезной, но не равна успешному запуску после восстановления. Автоматизация копирования фотографий не нужна.

## 4. Команды и повторное подключение

- История команд уже хранится в БД Bastion, но состояние раскатки `Bastion.Rollout` и часть результатов агента живут в памяти. Сохранять прогресс раскатки и агентские результаты до подтверждения их приёма.
- У каждой команды стабильный ID; повторная доставка не запускает update/restore/env_write второй раз. Явные состояния: ожидает, выполняется, завершена, ошибка, исход неизвестен.
- Сетевой push — не подтверждение сохранения результата. Нужен ответ Bastion после фиксации результата, затем агент может удалить локальную запись.
- После перезапуска агента или Bastion сверять реально выполняющуюся/завершённую операцию. Не повторять разрушительное действие автоматически при неизвестном исходе.
- Одна изменяющая операция на установку; параллельные команды из web и Telegram не обходят блокировку. Статус и необходимая диагностика не должны блокироваться долгим обновлением без объяснения.
- Таймаут процесса агента не доказывает остановку внешней команды Docker/восстановления: проверить управление дочерними процессами, учёт ещё выполняющихся операций и снятие блокировки.
- Совместимость протокола описать явно: версия, поддерживаемые действия и обязательные поля. Не определять поддержку бэкапа перед обновлением косвенно по наличию `rollback`.

## 5. Идентичность агентов и действия владельца

- Заменить общий токен подключения на индивидуальные реквизиты установки, привязанные к её ID. Сохранить простой сценарий первичного подключения через одноразовую регистрацию владельцем.
- Ключ отдельной установки можно отозвать/перевыпустить без смены всех агентов. Владение ключом одного сайта не разрешает регистрацию от имени другого.
- Не сохранять токены в логах, URL журналов и истории команд; учесть текущую передачу токена в query websocket.
- Агент с docker.sock — привилегированный компонент. Оставить ограниченный список действий и проверку аргументов; не добавлять произвольный shell/exec в панель.
- Действия из web и Telegram проходят один механизм авторизации и аудита. Чтение `.env`, запись настроек, восстановление и обновление имеют автора и результат, без сохранения секретного содержимого в журнал.
- В production отсутствие настроек Telegram не должно незаметно убирать второй фактор входа в Bastion. Явно отделить локальный dev-режим и выбранный владельцем production-способ входа/восстановления доступа.

## 6. Границы агента и мониторинга

- Инфраструктура остаётся у агента: контейнеры, диск, версия, запуск обслуживания, бэкап/restore БД.
- Бизнес-диагностику постепенно перенести из SQL по таблицам Delivest в закрытый версионированный endpoint приложения. Агент не должен ломаться при изменении структуры `orders.crm` или `app_logs`.
- Отсутствие бизнес-диагностики отличать от нулевого числа проблем; не возвращать владельцу ложное «всё хорошо» при сбое запроса.
- По [задаче подписок](franchise-feature-access.md) ошибки CRM остаются в ошибках филиала/франшизы; отдельные общие Telegram-тревоги Bastion для них отключаются. Падения приложения, сайта и инфраструктуры продолжают вызывать технические тревоги.

## Сценарии проверки

- Новый release появился в GHCR во время раскатки: все целевые установки получают первоначально выбранный выпуск.
- Образ отсутствует/нет доступа, не прошёл бэкап или загрузка конфигурации: работающие сервисы не затронуты.
- Приложение отвечает 404 или запустилось со старой версией: развёртывание не признаётся успешным.
- Ошибка запуска после миграций: корректный откат для совместимой схемы, понятный отказ от небезопасного отката для несовместимой.
- Две установки на одном хосте: обновление одной не уничтожает образы возврата другой.
- Обрыв связи, перезапуск Bastion/агента, повтор команды, timeout: нет двойного выполнения, прогресс и неизвестный исход видны.
- Поддельный instance_id с ключом другой установки отклоняется; отзыв ключа действует независимо от остальных агентов.
- Восстановление дампа проверено на отдельной БД, исходная production-БД проверкой не затрагивается.

После реализации выполнить обязательные проверки затронутых репозиториев (`mix precommit`, клиентские проверки, E2E по затронутому сценарию), обновить README/DEPLOY по фактическому поведению. Не заявлять, что конкретный production или GHCR проверен, пока соответствующая проверка не выполнена.
