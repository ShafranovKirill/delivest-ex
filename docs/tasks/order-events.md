# Задача: события заказа и outbox

Сейчас реакция на заказ — прямые вызовы после коммита. `StatusChange.finish/3` по очереди зовёт `Notifier`, `Audit`, `Couriers.order_moved`, `Kitchen.order_accepted`, `alert`. Если процесс упадёт между коммитом и вызовом, реакция потеряна. Каждая новая интеграция — ещё строка в ядре.

С деньгами так нельзя: оплата прошла, а чек не пробит; возврат проведён, а CRM не узнала.

## Решения

| Вопрос | Решение |
|---|---|
| Где пишется событие | В той же транзакции, что и изменение. Нет коммита — нет события, есть коммит — событие точно будет обработано |
| Чем доставляется | Oban: задачи вставляются в той же транзакции. Отдельный брокер не нужен, Oban и так в Postgres |
| Гарантия | Не меньше одного раза. Каждый подписчик идемпотентен |
| Порядок | Не гарантируется. Подписчик читает текущее состояние заказа, а не только данные события |
| Кто подписан | Реестр `Events.Registry`, как `Crm.Registry`: подписчик объявляет, какие события слушает |
| PubSub для экранов | Остаётся после коммита. Ему не нужна надёжность: экран перечитает данные |
| Входящие вебхуки | Inbox: сначала запись `(провайдер, id события)` с уникальностью, потом обработка задачей |
| Эхо | Изменение, пришедшее от провайдера, не уходит обратно ему же. В событии `actor` — источник (`{:crm, :iiko}`), подписчик провайдера такие события пропускает. Иначе статус из iiko вернётся в iiko правкой, а та — новым вебхуком |
| Что поменялось | `order.updated` несёт список изменённых полей и старые значения: iiko и r_keeper правят заказ точечно (`change_comment`, `PatchOrder`), а не пересылают целиком |

## Журнал событий

Таблица `domain_events`:

| Поле | Что |
|---|---|
| `id` | UUID v7, сортируется по времени |
| `type` | `order.created`, `order.status_changed`, `order.updated`, `payment.succeeded` … |
| `aggregate_type`, `aggregate_id` | `order` и id заказа |
| `branch_id` | Для выборок и прав |
| `payload` | Что случилось: `from`, `to`, `source`, изменённые поля, суммы. Версия схемы — `v` |
| `actor` | Кто: сотрудник, курьер, канал, CRM, система |
| `inserted_at` | Момент |

Журнал не меняется и не удаляется вместе с заказом. Аудит (`Audit`) остаётся для людей, журнал — для машин. Позже по журналу строятся исходящие вебхуки и публичное API.

## Подписчик

```elixir
@behaviour Delivest.Events.Subscriber
def key, do: :couriers
def events, do: ["order.status_changed", "order.created"]
def handle(%Event{} = event), do: ...
```

- `Events.emit(multi, type, aggregate, payload, actor)` — шаг `Ecto.Multi`: строка журнала и по задаче `Events.DeliverWorker` на каждого подписчика.
- `DeliverWorker` уникален по `(event_id, subscriber)`, повторы с backoff, после исчерпания — тревога в админке и запись в логи.
- Подписчик сам решает, что делать с ошибкой: `:ok`, `{:error, ...}` — повтор, `{:cancel, ...}` — постоянная.

## События

| Событие | Когда | Подписчики |
|---|---|---|
| `order.created` | Заказ создан | CRM, кухня, push, каналы |
| `order.status_changed` | Переход автомата, в том числе откат | Курьеры, кухня, CRM, каналы, чеки, push |
| `order.updated` | Состав, адрес, оплата, время | CRM, Яндекс Доставка, оплаты (пересчёт долга) |
| `order.cancelled` | Отмена | Курьеры, оплаты (возврат), каналы |
| `payment.succeeded`, `payment.failed` | Оплата | Чеки, заказ (автопринятие), push |
| `refund.succeeded` | Возврат | Чеки, CRM |
| `receipt.done`, `receipt.failed` | Чек | Курьер (QR), тревога |

## Перевод существующего

1. `Events`, журнал, `DeliverWorker`, реестр.
2. `StatusChange`, `Create`, `Update`, отмена и откат пишут события.
3. `Couriers.order_moved`, `Kitchen.order_accepted`, push, тревоги — подписчики.
4. CRM: `Crm.create_order` уже ставит задачу в транзакции — перевести на событие `order.created`.
5. Вебхуки Frontpad, Яндекс Еды, Яндекс Доставки — через inbox.

## Тесты

- Подписчик падает — событие обрабатывается повтором, второй раз эффекта нет.
- Транзакция откатилась — ни события, ни задач.
- `Oban.Testing` в режиме `:manual`, проверка `assert_enqueued`.
