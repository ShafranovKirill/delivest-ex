# Segments, first release

Staff create manual or dynamic customer groups. Groups are independent from future marketing policies. A group has immutable type (`manual` or `dynamic`) and immutable scope (`franchise` or selected branches). The selected branches are immutable. Name and dynamic conditions can be edited. A franchise group evaluates enabled branches of this installation; disabled branches contribute no metrics. A branch group is visible only when every branch is enabled and entirely within the staff member's permitted branch set.

## Permissions and feature gate

- `segments.read`: list groups and private members.
- `segments.manage`: create/edit groups and manage manual members.
- `segments.network`: view or create franchise-scope groups. The franchise manager preset receives it; the branch manager preset does not.
- `admin` grants business permissions, but feature switches are host-managed through `Delivest.Features`. Staff have no switch endpoint. Parent and branch gates must both be enabled for branch calculations. Read and write domain APIs check the gate; writes are fenced again in a short transaction against the captured generation.
- Branch staff may add a client only if that client has a nondeleted order in every group's eligible branch set (at least one branch). This is also checked when reading branch-group members. A franchise manager can add any active, nondeleted client. Blocked/deleted clients are omitted from results and new membership.

## Rule format

Version 1 is a JSON object with exactly `version: 1`, `match: "all" | "any"`, and 1–8 `conditions`. Each condition has exactly `metric`, `op`, and nonnegative integer `value`. Metrics: `days_since_last_order`, `order_count`, `total_spent`, `avg_check`. Operators: `eq`, `gte`, `lte`. No arbitrary SQL or nested expression is accepted. Money is stored in integer minor units; the staff form accepts rubles and converts exact kopecks. Average check uses integer division of total net spend by completed order count. Last-order age is the number of full elapsed 24-hour periods; a client with no completed order never matches that metric. Other metrics for such clients are zero. For local groups, a client must have any nondeleted order in a selected branch to enter the candidate universe, even if their completed-order count is zero.

Completed orders with `deleted_at IS NULL` count, including linked guest orders. Cancelled and unfinished orders do not count. `total_spent` sums each completed order's `total_amount` minus succeeded refunds for that order, clamped to zero per order. `avg_check` is net spend divided by the completed-order count. The date source for the last completed order is `orders.inserted_at`, matching existing Analytics date selection. Existing Analytics reports are unchanged.

## Refresh and consistency

There is one `segments.refresh` background schedule for the installation. The runner calls `Delivest.Segments.Refresh.perform(:franchise, context)` daily. No segment-owned cron or one-job-per-group scheduler exists. When there are no dynamic groups or no enabled relevant branches, no customer metric scan runs.

The first run for an enabled branch walks active clients by UUID keyset in batches of 250 and computes metrics from that client's indexed order history. A metrics row records the presence of any nondeleted order in a branch, even if completed-order count is zero; this lets local groups find their eligible clients without rereading order history. Subsequent runs copy the published metrics snapshot in batches and recalculate only dirty clients. Database triggers on order and refund INSERT/UPDATE/DELETE mark a `(branch_id, client_id)` dirty row transactionally when both gates are enabled. Unrelated order edits do not mark dirty. A global sequence gives each dirty change a never-reused revision. During disabled periods triggers create no work; re-enable changes the feature generation and forces a new baseline. Refund history is aggregated per selected order using the order refund index, with no duplicate order joins and no scan of all refunds per group. Group evaluation reads the shared staged customer metrics snapshot rather than rescanning order history.

Metrics and dynamic membership are staged under new snapshot UUIDs. A short guarded transaction checks the background job owner, parent and branch gate generations, and each group's revision before moving published pointers. A failed or revoked run retains the previous published pointers. Dirty rows are acknowledged only if their global revision still matches the captured revision; a concurrent change remains queued. Post-publication acknowledgement and orphan cleanup are best effort; an interrupted cleanup leaves safe redundant dirty rows and staging data for the next run. Each cleanup deletion is bounded and fenced by the background owner. The runner applies a PostgreSQL statement timeout and total job timeout, with pressure and revocation checkpoints between batches. Last successful refresh is visible to staff; errors are generic in the UI and detailed only in server logs.

## Operations and limits

Routes: `/staff/segments`, `/staff/segments/new`, `/staff/segments/:id`, `/staff/segments/:id/edit`. The staff navigation hides the link while the parent feature is off; direct routes and events recheck. Lists and member pages are bounded at 50 rows and use UUID keyset pagination. Manual group creation can atomically add up to 100 selected clients after validating their status and scope.

The first baseline still reads each active client's lifetime completed orders once per enabled branch. This is necessary after initial enable or re-enable; installations with very large histories should measure baseline duration against the 15-minute job timeout and 30-second statement timeout. The refresh batches prevent an unbounded application-memory client list, but one client's exceptionally large order history can still exhaust a statement budget. Subsequent unchanged daily runs copy metrics rows and evaluate groups without rereading order history. The synthetic benchmark under `scripts/bench/segments.exs` records representative query plans and relative timings, not a production SLA.

Synthetic result on 2026-11-10, isolated PostgreSQL 16.14 test database on an Intel Core i7-9700, Elixir 1.19.5, with 1,000 active clients, 5 enabled branches, 5,000 completed orders, one network group and three branch groups: baseline 1.462 s and 20 order SELECTs; unchanged refresh 0.710 s and zero order SELECTs; one changed client 0.893 s and one order SELECT. `EXPLAIN (ANALYZE, BUFFERS)` for the actual net-refund metrics query over 250 client IDs in one branch used `orders_branch_id_inserted_at_index` and `order_refunds_order_id_index`, returned 250 metric rows in 0.611 ms, and reported 532 shared buffer hits. These timings are local synthetic measurements, not a production SLA; the order index scan still filtered 750 rows from a 1,000-order branch, so larger branches need their own measurements.

An independent coordinator run on a fresh `segmentsbenchroot20261110` partition reproduced the order-query counts (20 / 0 / 1), with timings 7.522 / 2.873 / 0.717 seconds and actual aggregate plan execution 0.663 ms. The timing variation is material: these exploratory runs establish query reuse, not a stable latency target or maximum supported capacity. The final server `mix precommit` passed 1,496 tests with zero failures (7 excluded) on another fresh test partition. The agent policy-restore checks passed 35 tests, including the real two-database policy-preservation integration.
