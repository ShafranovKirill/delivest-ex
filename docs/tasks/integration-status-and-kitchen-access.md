# Задача: понятные состояния интеграций и запрет доступа к выключенной кухне

## Проблема

После ввода API-ключей Frontpad и других сервисов админка показывает «Подключено», даже когда отправка заказов выключена. Сохранённые реквизиты, проверка связи и реальное использование сервиса смешаны: оператор не понимает, куда сейчас отправляются заказы и какие функции работают.

У выключенной кухни доступен URL `/staff/b/:branch_slug/kitchen`: вместо отказа открывается экран с заглушкой. Более того, `KitchenLive.Index.mount/3` регистрирует экран в `KitchenPresence` до проверки `Kitchen.working/1`. Ссылка в навигации учитывает режим шлюза, но не `kitchen.enabled`.

Нужно исправить оба случая. В рамках задачи наличие настроек никогда не означает включение функции.

## Связь с доступом франшизы

По [задаче ручных подписок](franchise-feature-access.md) владелец Delivest управляет разрешёнными функциями через Bastion. Если интеграция или кухня не разрешена франшизе либо выключена владельцем, скрывать модуль полностью: без карточки, заглушки и статусов подключения. Правила ниже применяются к разрешённым функциям. Роли сотрудников, настройки филиала и готовность API дополнительно ограничивают доступ, но не выдают закрытый модуль. Дата оплаты сама ничего не отключает.

## 1. Три независимых состояния интеграции

В списке интеграций и внутри настроек показывать отдельно:

| Что | Значения | Источник |
|---|---|---|
| Данные для подключения | «Не заполнены», «Заполнены частично», «Заполнены» | Полнота необходимых реквизитов конкретного провайдера |
| Проверка связи | «Не проверена», «Связь проверена», «Ошибка доступа», «Нет связи» | Результат проверки текущих реквизитов, время проверки |
| Использование | Конкретные функции: «Отправка заказов: выключена», «Отправка заказов: включена», «Стоп-лист: …» | Сохранённые переключатели и правила работы филиала |

Правила:

- Убрать общее «Подключено» / «Интеграция включена» как обозначение заполненных ключей или успешного запроса. Использовать формулировки из таблицы.
- Проверка связи подтверждает только доступность API и доступ по текущим реквизитам. Она не включает отправку, приём заказов, оплату или синхронизацию.
- Зелёный индикатор связи рядом с «Отправка заказов: выключена» допустим: подписи должны однозначно объяснять разные факты. Не давать карточке общий зелёный статус «Включено» по факту наличия ключей.
- «Отправка заказов: включена» означает сохранённое разрешение отправлять, а не гарантию доставки каждого заказа. Ошибку API показывать отдельно: «Отправка заказов: включена» + «Нет связи».
- При неполной конфигурации и уже включённой функции показывать «Включена, но не готова: заполните …». Не скрывать конфликт и не выдавать его за штатно работающую интеграцию. Новое включение с неполными обязательными данными отклонять на сервере.
- При смене ключа, адреса API, магазина или других реквизитов старый успешный результат не подтверждает новые настройки: сбросить/пометить проверку как устаревшую. Не показывать старый успех или ошибку как актуальную проверку новых реквизитов. При неуспешном сохранении результат не сбрасывать.
- Если текущий `health_check` проверяет только заполненность полей, это не проверка связи. До настоящего запроса показывать «Связь не проверена»; не вызывать платную/изменяющую данные операцию ради проверки.
- Предупреждения о расхождении меню, платежей и т. п. выводить отдельной строкой «Требует внимания», а не подменять ими состояние переключателя. Если health-модель не хранит отдельный результат связи, не додумывать его по предупреждению.
- Указывать область действия: «Для всей сети» или «Филиал: …». Общие ключи не означают включение функции во всех филиалах.
- Одинаковые подписи и правила во всех карточках, на страницах провайдеров и маршрутов. Русские и английские переводы обновить вместе.

Пример Frontpad после сохранения рабочего ключа без галочки отправки:

```text
Frontpad · Филиал: Центральный
Данные для подключения: заполнены
Проверка связи: успешна · 02.11.2026 14:30
Отправка заказов: выключена
Стоп-лист: выключен
```

Если проверку не запускали, вместо успешной проверки — «Связь не проверена». Пример времени иллюстративный; в интерфейсе выводить фактическое время в часовом поясе филиала.

## 2. Какие функции считать включёнными

Не добавлять универсальную новую галочку «Включить интеграцию» поверх существующих настроек. Использовать реальные переключатели и единые доменные правила; не собирать независимую бизнес-логику в шаблонах.

| Сервис | Что показывать как использование |
|---|---|
| Frontpad, iiko, r_keeper | Отправка новых заказов в выбранную CRM, источники заказов, источник меню, автоматическая синхронизация стоп-листа |
| ЮKassa | Ключи магазина — для всей сети; онлайн-оплата — отдельно для текущего филиала по настройкам «Финансы → Оплата». Ссылка на это место включения |
| Zvonok | Вход клиентов по звонку по фактическому `enabled`; заполненные ключи не включают вход |
| DaData | Подсказки адресов по фактическому `enabled` и полноте настроек |
| Яндекс Еда | Приём заказов для филиала; отдельно оперативная пауза/недоступность. Ключи сети не включают приём в филиале |
| Яндекс Доставка | Автовызов курьера по выбранному источнику курьеров филиала; наличие токена само по себе его не включает |
| АТОЛ | Кто выдаёт чеки: наша касса / CRM / иной текущий режим; готовность реквизитов отдельно. Не показывать собственную отправку чеков включённой в режиме, где их выдаёт CRM |

Для CRM:

- Отправка разрешена только при `crm.enabled == true` и совпадении `crm.provider` с данной карточкой. Достаточность ключей — отдельная проверка готовности.
- Если выбран другой провайдер, явно писать: «Отправка в Frontpad: выключена. Выбрана CRM: iiko».
- Источники (`crm.sources`) перечислять человекочитаемо. При пустом списке писать «Источники заказов не выбраны»: новые заказы не отправляются, даже если общий переключатель включён.
- Источник меню и стоп-лист имеют собственные правила. Не обещать, что снятие галочки отправки выключает все обращения к API. Если автоматический стоп-лист фактически зависит от активной CRM, при снятой галочке показывать «Не работает: отправка в эту CRM выключена», а не только состояние вложенного `sync_stops`.
- Ручная проверка API, чтение/сверка каталога могут оставаться доступны при выключенной отправке. Объяснить это коротко: «Можно проверить подключение и сопоставить меню. Новые заказы не отправляются».
- Сохранение ключей и ручная проверка не меняют `enabled`, источники, провайдера маршрутизации или режим филиала сами по себе. Проверить существующий `settings_params/1`, который подставляет provider: сохранение выключенного провайдера не должно незаметно переключать активную CRM. При явной смене активной CRM форма должна называть это действие.
- Раздел «Маршруты заказов» использует те же правила и показывает фактический получатель и источники, а не просто наличие выбранного provider.
- Не менять жизненный цикл уже отправленных заказов: выключение отправки новых заказов не должно прекращать необходимые подтверждения, обновления и отмены по ранее отправленным. Подпись — именно «Отправка новых заказов». Для уже созданных заданий проверить существующую семантику и явно пояснить её в настройках, без скрытого массового удаления заданий.

Существующие сохранённые значения переключателей при выпуске сохраняются. Ничего не включать автоматически. Не менять режим шлюза из-за наличия ключей или результата проверки.

## 3. Доступ к кухне

Доступ к рабочей странице кухни разрешён только при одновременном выполнении условий:

1. Сотрудник авторизован и имеет доступ к выбранному филиалу.
2. Есть право `orders.cook`.
3. `branch.info.kitchen.enabled == true`.
4. Кухня принадлежит нашему приложению: `Gateway.own?(branch, :kitchen)`.

Использовать общий предикат доступности на базе существующего `Kitchen.working/1` / `working?/1`, не создавать расходящиеся проверки для навигации, страницы и действий. Сотруднику нужны и право, и включённая функция; администратор не обходит выключенную настройку.

### Вход и навигация

- При выключенной кухне скрыть ссылку «Кухня» в меню и прочие кнопки открытия экрана.
- Прямой GET, LiveView-навигация, переподключение и старая закладка не открывают рабочий экран. Проверка выполняется на сервере до загрузки заказов, подписок, запуска таймеров и регистрации presence.
- Перенаправить на доступную сотруднику страницу с сообщением «Кухня выключена в настройках филиала». При кухне CRM — «Кухня работает в CRM и недоступна в приложении».
- Для сотрудника только с правами кухни не отправлять на недоступный dashboard или обратно на `/staff`, который снова перенаправляет на кухню. Использовать выбор филиала с объяснением, а при отсутствии доступных рабочих филиалов — сообщение обратиться к администратору и возможность выйти.
- Проверить автоматический переход после входа и выбора филиала: `StaffHomeController`, `StaffActiveBranchController`, `StaffBranchPath` и страницу выбора. Они не должны вести сотрудника на выключенную кухню или создавать цикл редиректов. Редирект сам по себе не даёт доступа к настройкам филиала.
- Настройки кухни остаются доступны сотрудникам с соответствующими правами управления филиалом.

### Кухню отключили при открытом экране

- После успешного сохранения настройки/смены режима филиала уведомить открытые кухонные сессии через PubSub. Перечитать актуальную доступность и перенаправить с тем же объяснением.
- Убрать экран из `KitchenPresence`, прекратить кухонные подписки и таймеры при уходе/завершении процесса; отключённый экран не должен показываться оператору как работающая кухня.
- До обработки уведомления пользователь не может обойти запрет старым событием `ready` или `undo`: проверка актуальной доступности нужна в доменных командах, не только в LiveView.
- Отложенный `ReadyWorker` тоже перепроверяет доступность перед изменением заказа. Если кухня уже выключена или передана CRM, не переводить заказ в «Готов»; такое задание завершить без изменения и не оживлять после повторного включения.
- Отключение кухни само по себе не отменяет заказы и не меняет их статусы.

## Проверка и критерии приёмки

Интеграции:

- На Frontpad, iiko и r_keeper заполненные ключи при снятой галочке показывают выключенную отправку. После успешной проверки связи она остаётся выключенной.
- При включении меняется только соответствующее использование; переключение филиала показывает его настройки. Ключи общей интеграции отображаются как общие, включение функции филиала — отдельно.
- Заполнено частично, заполнено без проверки, успешная проверка, ошибка ключа, недоступность API и предупреждение о расхождении различимы и не подменяют переключатель.
- Смена ключей сбрасывает актуальность проверки. Чтение страницы настроек, проверка API и сохранение реквизитов не включают отправку и не меняют маршрутизацию.
- Если активна iiko, сохранение ключа Frontpad без явной смены CRM оставляет iiko активной.
- Пустые sources, независимая синхронизация, выключенная оплата филиала при ключах ЮKassa и неактивный вызов курьера при токене Яндекса отображаются без противоречий.
- Успех проверки только заполненности реквизитов не выдаётся за успешный запрос к API.
- Пользователь без прав изменения видит состояния, но не может менять переключатели или запускать недоступные ему действия через поддельные события.

Кухня:

- При выключенной кухне ссылка скрыта, прямой URL и подключение LiveView перенаправляют. Рабочие данные не загружаются, presence не создаётся.
- При включённой кухне сотрудник с нужными правами открывает экран; без прав или доступа к филиалу отказ сохраняется.
- Администратор тоже не попадает на выключенный рабочий экран.
- В режиме шлюза вход запрещён, даже если сохранено `kitchen.enabled: true`.
- Открытый экран закрывается после отключения кухни/передачи её CRM; presence удаляется. Старые события и отложенный ReadyWorker не меняют заказы.
- Повторное включение возвращает доступ, но не выполняет отменённые при отключении действия.
- Вход сотрудника кухни и смена филиала не дают циклов редиректа и не отправляют его на страницу без прав.

Расширить существующие `test/delivest_web/live/staff/integration_live/*_test.exs`, тесты health/settings, `test/delivest_web/live/staff/kitchen_live/index_test.exs`, `gateway/gateway_mode_test.exs`, доменные тесты кухни и проверки начальных редиректов. После реализации выполнить `mix precommit`.

## Порядок реализации

1. Общие правила и представление трёх состояний; проверить отсутствие побочных переключений при сохранении реквизитов.
2. Карточки интеграций, страницы провайдеров, маршруты, области действия и переводы.
3. Серверный запрет кухни, навигация и начальные редиректы.
4. Отключение открытых сессий, presence, команды и отложенные задания.
5. Проверки из критериев приёмки и обновление связанных задач при необходимости.
