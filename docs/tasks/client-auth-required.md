# Задача: обязательный вход перед оформлением заказа

Статус: к реализации. Репозитории: `server/`, `client/`. Настройка действует на всю франшизу и относится только к созданию клиентского заказа. История, адреса и бонусы сохраняют свои текущие правила входа. Смежная задача по способам звонка описана в [client-polish.md](client-polish.md).

## Цель и текущее состояние

Администратор франшизы управляет галочкой «Требовать вход для оформления заказа». При выключенной галочке гость проходит существующий сценарий. При включённой клиент должен войти до создания заказа, а корзина и заполненные поля сохраняются. Текущий `client_auth` в `/client/franchise` отражает доступность Zvonok и не означает обязательность входа.

Точки входа сервера: `lib/delivest/franchise/settings.ex`, `lib/delivest_web/live/staff/franchise_live/settings_form_component.ex`, `lib/delivest_web/controllers/client/franchise/{franchise_controller,franchise_json}.ex`, `lib/delivest_web/schemas/franchise_schemas.ex`, `lib/delivest_web/controllers/client/order/order_controller.ex`. Точки входа клиента: `src/modules/order/{views/CheckoutView.vue,stores/order.store.ts,components/OrderForm.vue}`, `src/modules/cart/components/CartComponent.vue`, `src/modules/auth/{stores/auth.store.ts,components/AuthModal.vue}`, ответ франшизы и сгенерированные `src/api/types.ts`.

## Шаги и границы

1. Добавить `client_auth_required` в `franchise_settings` с миграцией `NOT NULL DEFAULT false`, в Ecto schema и разрешённые поля changeset. Старые записи и свежая установка получают `false`. Показывать галочку в настройках франшизы с пояснением, что вход требуется при оформлении. Сохранять её тем же защищённым механизмом обновления настроек.
2. При включении проверить наличие настроенного способа входа по существующим локальным настройкам Zvonok. Не выполнять сетевой health-запрос при сохранении галочки, потому что временный сетевой сбой не должен мешать изменению настроек. Если вход не настроен, отклонить сохранение с ясной ошибкой в форме. При последующей временной недоступности провайдера не открывать обходной гостевой путь. Показать понятную ошибку клиенту и сохранить корзину для повторной попытки.
3. Вернуть отдельное `client_auth_required` в `/client/franchise`, обновить JSON, OpenAPI schema и генерируемые типы клиента. Существующее поле `client_auth` и его значение оставить совместимыми для старых клиентов. В UI использовать отдельный признак обязательности.
4. На сервере проверять авторизованного `current_client` в `OrderController.create/2` до `Oms.create_order/2`, начала платежа и иных побочных действий. Для гостя возвращать HTTP 401 через существующий `ApiError` со стабильным кодом `client_auth_required`, который клиент распознаёт. Проверить пути для онлайн-оплаты и бонусов. Клиентская проверка не заменяет серверную.
5. При нажатии «Оформить» открывать текущую форму входа, если настройка включена и клиент гость. После успешного входа возвращать к оформлению с той же корзиной, филиалом, способом получения и введёнными данными, не создавая заказ автоматически без повторного подтверждения пользователем. Учесть закрытие модального окна, отмену входа, обновление страницы и истечение сессии перед отправкой.
6. Если настройка выключена, не добавлять лишний шаг входа. Корзина, каталог и просмотр акций остаются доступными гостю при обоих значениях. Текущий вход для адресов, истории и бонусов не менять.

## Приёмка и проверка

- Миграция существующей базы оставляет гостевое оформление включённым. Переключатель сохраняется, считывается API и виден клиенту без ручной правки сгенерированных схем.
- Прямой `POST` создания заказа гостем при включённой галочке отклоняется до записи заказа и начала оплаты. При выключенной галочке существующий гостевой сценарий проходит.
- Авторизованный клиент оформляет заказ при обоих значениях. После успешного входа корзина и заполненная форма сохранены, а дубли заказа не возникают.
- Невозможно включить обязательный вход без работоспособного способа входа. При временной ошибке провайдера клиент видит причину и может повторить вход после восстановления.
- Проверить серверные controller и settings тесты, клиентские store/component проверки, `mix precommit` в `server/`, `pnpm type-check` и `pnpm lint` в `client/`, затем E2E сценарии гостя и входа перед checkout.
