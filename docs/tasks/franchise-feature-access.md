# Задача: ручные подписки франшиз и управление доступом из Bastion

Статус: к реализации. Изменения затрагивают Delivest, Delivest Agent и Delivest Bastion.

## Цель и принятые решения

Владельцу Delivest нужна собственная панель контроля: собрать набор функций, назначить его франшизе, вручную указать, до какого числа оплачено, и отправлять напоминания в Telegram. Клиенты ресторана и сотрудники франшизы не покупают подписку через приложение и не управляют её составом.

| Вопрос | Решение |
|---|---|
| Кто управляет | Только владелец Delivest через существующий закрытый Bastion |
| Кому назначаем | Франшизе, с применением ко всем её филиалам |
| Как собираем | Шаблон подписки с набором функций + индивидуальные изменения для франшизы |
| Оплата | Владелец вручную меняет дату «Оплачено по»; автоматической оплаты нет |
| Дата прошла | Отметка просрочки в Bastion и напоминания в Telegram. Доступ не меняется |
| Выключение | Только явное действие владельца: функция глобально или для выбранной франшизы |
| Недоступная функция | Полностью скрыта во всех интерфейсах франшизы, включая раздел «Интеграции» и редактор ролей. Без замков, рекламы тарифа, кнопок покупки и заглушек |
| Bastion временно недоступен | Приложение работает по последней успешно сохранённой конфигурации доступа, без ограничения по времени отсутствия связи |
| Ошибки Frontpad и других бизнес-интеграций | Сохраняются в ошибках филиала и сводке франшизы; отдельные общие Telegram-тревоги Bastion по ним отключаем |

## 1. Каталог функций и permissions

Создать явный реестр функций со стабильными ключами и человекочитаемыми названиями. Первые группы:

- Интеграции: Frontpad, iiko, r_keeper, Яндекс Еда, Яндекс Доставка, ЮKassa, АТОЛ, Zvonok, DaData — отдельные разрешения на каждый сервис.
- Приложение доставщика / рабочее место курьера.
- Живые карты и отслеживание курьеров. Отличать от обычной карты выбора адреса: это разные возможности.
- Кухня, экран выдачи, касса.
- Бонусная программа и другие самостоятельные модули по итогам инвентаризации существующей навигации и API.

Не превращать каждую кнопку в отдельную продаваемую функцию. Перед реализацией составить соответствие «функция → страницы → API → фоновые операции → permissions» на основе реального кода.

Использовать существующую систему permissions для проверки действий, добавив верхний уровень допуска франшизы. Не выдавать коммерческий доступ через редактируемые франшизой роли: локальный администратор с `admin` тоже не обходит запрет владельца.

Общее правило доступа к действию:

```text
функция разрешена владельцем глобально
  И функция входит в набор франшизы
  И функция не выключена владельцем для этой франшизы
  И сотруднику разрешено действие в нужном филиале
  И соблюдены настройки и ограничения режима филиала
```

Дата оплаты в это выражение не входит. Наличие API-ключей также не выдаёт функцию.

- Верхний допуск проверять в общем слое авторизации и доменных операциях, а не только в меню.
- Скрывать относящиеся к недоступной функции permissions из редактора ролей. Сохранённые роли не переписывать и не удалять их права: пока функция закрыта, такие права не действуют; после возврата функции роли продолжают работать.
- Неизвестные ключи функций и попытки выдать права на закрытый модуль через поддельный запрос не дают доступа.
- Существующая настройка «Отправлять заказы» и другие локальные галочки остаются. Доступ по подписке разрешает использовать настройку, но сам её не включает.
- При недоступном модуле скрывать его карточку в интеграциях, пункты меню, вкладки, кнопки, поля настроек, виджеты, разрешения и предложения перейти в модуль. Прямой URL / API дают обычный отказ доступа без рекламы тарифа и без содержимого закрытого модуля. Настройки и секреты закрытой функции не попадают в ответы API.
- Правило относится и к самостоятельному приложению доставщика, гостевым экранам, клиентской витрине и живым сокетам. Публичные endpoints не должны полагаться на staff permissions.
- Действия, которые закрываются по доступу, не должны продолжать работать через фоновые задания или уже открытые соединения.

## 2. Управление в Bastion

Добавить отдельный раздел «Франшизы / Подписки» в существующую панель. Не делать новый отдельный сервис биллинга или клиентский кабинет оплаты.

Для франшизы хранить:

- стабильный ID, название, связь с установкой/установками Delivest;
- назначенный шаблон подписки, итоговый набор функций и индивидуальные отключения;
- дату «Оплачено по» включительно и часовой пояс франшизы;
- Telegram-получателя напоминаний, включение напоминаний, внутреннюю заметку;
- ревизию конфигурации доступа, время изменения, состояние доставки в приложение.

Не отождествлять ID франшизы с UUID агента, доменом или ID локальной настройки: переустановка агента и смена домена не создают новую подписку. Привязку новой установки выполняет владелец явно; агент не назначает себе чужую франшизу.

Интерфейс владельца:

1. Создать именованный шаблон набора функций.
2. Назначить его франшизе и при необходимости изменить отдельные функции.
3. Указать дату оплаты вручную.
4. Сохранить и увидеть, какая ревизия фактически применена на установке.
5. Явно включить/выключить отдельную функцию для франшизы либо глобально для всех.

Назначение шаблона копирует его состав в набор франшизы. Последующее редактирование шаблона само по себе не меняет действующие наборы: для применения изменений к выбранным франшизам нужно отдельное явное действие со списком изменений. Глобальное выключение функции владельцем имеет приоритет над любым шаблоном и индивидуальной выдачей.

В карточке владельца отдельно видны «Доступ назначен», «Доставка ожидается», «Применено», «Ошибка доставки». Не показывать желаемое состояние как уже применённое. Изменение доступа, даты, контактов и глобальных выключателей записывать в аудит: кто, когда, что изменил. Содержимое секретов не журналировать.

## 3. Доставка доступа в приложение

- Bastion — источник назначенного владельцем доступа. Delivest хранит последнюю принятую конфигурацию локально и проверяет её без сетевого обращения на каждое действие.
- Доставка идёт через аутентифицированный канал конкретной установки; агент может быть транспортом, но решение о доступе принимает сервер Delivest. Не реализовывать это переписыванием `.env` и перезапуском контейнеров.
- Идентичность франшизы и установки проверяется получателем. Изменение конфига подписки недоступно через публичный API, настройки франшизы и обычную staff-сессию.
- Ревизии монотонные, повторная доставка идемпотентна. Старая ревизия не отменяет новое отключение. Применение атомарно, после сохранения возвращается подтверждение; при восстановлении связи доставляется последнее состояние.
- Успешное применение инвалидирует кеши авторизации/навигации и уведомляет открытые сессии. Открытая страница не сохраняет возможность выполнять новые запрещённые действия.
- Резервное восстановление старой БД не должно навсегда возвращать старые права: после соединения синхронизировать актуальную ревизию с Bastion. До синхронизации явно показывать владельцу фактически применённую конфигурацию.
- Первая установка требует явного назначения набора владельцем. При внедрении на действующие установки подготовить миграционный набор из уже разрешённых возможностей и согласованную привязку; не выключить всё из-за отсутствия новой записи.
- Не вводить срок годности локального допуска, автоотключение из-за неоплаты или из-за отсутствия heartbeat. Недоступный Bastion — проблема управления, а не основание останавливать ресторан.

### Ручное выключение во время работы

Запрет начинает действовать для новых операций после применения конфигурации. Скрыть UI сразу. Ранее принятые заказы, платежи и внешние обязательства не бросать: необходимые возвраты, чеки, отмены и завершение уже начатой синхронизации выполняются ограниченным внутренним путём без доступа к новым операциям модуля. Для каждого такого исключения указать конкретные операции при составлении карты функций; не оставлять общий обход запрета для фоновых задач.

Выключение модуля не удаляет данные, роли, ключи и историю. Повторное разрешение возвращает возможность использовать сохранённые настройки. Истёкшая дата оплаты вообще не запускает этот сценарий.

## 4. Telegram: пора оплатить

- Отправлять напоминание в привязанный владельцем чат представителя франшизы. Если чат не привязан, уведомить владельца о ненастроенном получателе, а не считать отправку клиенту успешной. У существующего владельца оставить сводку предстоящих/просроченных оплат в Bastion.
- Начальные интервалы: за 3 дня, в последний оплаченный день и на следующий день после окончания; затем не чаще раза в неделю, пока дата не продлена. Позволить владельцу отключить напоминания для конкретной франшизы.
- «Оплачено по 15 ноября» означает весь этот день в часовом поясе франшизы. Просрочка начинается 16 ноября; пустая дата означает «Не указана», без выдуманной просрочки.
- Сообщение: название франшизы, дата оплаты и просьба связаться с владельцем для продления. Без угроз автоотключения и без кнопки онлайн-оплаты.
- Очередь отправки с защитой от дублей по франшизе, дате оплаты и виду напоминания. При выполнении перечитывать дату: после ручного продления старое напоминание не отправлять. При назначении уже просроченной даты не рассылать задним числом все пропущенные напоминания.
- Ошибка Telegram видна владельцу, повторяется с ограничением и не меняет доступ к функциям.

## 5. Бизнес-ошибки по филиалам и франшизе

Ошибки Frontpad, iiko, r_keeper и других бизнес-интеграций не теряются, но не превращаются в общую техническую аварию установки в Bastion.

- В Delivest добавить/довести раздел «Ошибки» филиала и сводку по всей франшизе. Если есть подходящий существующий журнал, расширить его вместо создания дублирующего.
- У ошибки есть ID, филиал (либо явно уровень всей франшизы), сервис, связанный заказ, время, понятная причина, состояние и ссылка на заказ/интеграцию. Сетевые настройки/проверки связи общих интеграций относятся к франшизе, ошибки конкретных заказов — к филиалу заказа.
- Оператор видит ошибки доступных ему филиалов; сводку всей франшизы — только с соответствующими правами. Секреты и сырые чувствительные payload не выводить.
- Ошибка заказа не должна исчезать только из-за возраста более 24 часов. Сохранять её до успешного восстановления или явной отметки «Обработано вручную». Отличать такую отметку от фактической успешной доставки в CRM.
- В Bastion отключить отдельные Telegram-уведомления `CrmAlerts` о бизнес-ошибках заказов. Сводные счётчики/метки филиалов и франшизы можно оставить в карточке установки как прикладную информацию, отдельно от состояния инфраструктуры.
- Технические тревоги Bastion (сайт недоступен, контейнер упал, диск, бэкап, сбой развёртывания) сохранить. Счётчик общих ошибок приложения не должен повторно превращать известную обработанную бизнес-ошибку CRM в техническую тревогу. Настоящие падения кода адаптера остаются техническими ошибками.
- Не отключать отправку в Frontpad и не менять доступ/подписку автоматически по факту ошибки.
- При ручном закрытии модуля не показывать франшизе его историю как отдельный доступный раздел: владельцу Bastion сохраняется диагностическая информация, а по незавершённому заказу остаётся необходимая общая ошибка исполнения без ссылок, открывающих закрытый модуль.

## Проверки

- Набор франшизы разрешает функцию, но её локальная галочка выключена: функция не запускается сама.
- Закрытый модуль отсутствует в UI, редакторе ролей, API-описании доступных возможностей и самостоятельных приложениях. Прямые запросы и старые события не обходят запрет, в том числе от локального администратора.
- Глобальный запрет владельца сильнее шаблона; изменение шаблона без явного применения не меняет действующие подписки.
- Дата оплаты прошла, Telegram недоступен или Bastion отключён: доступ и выполнение заказов сохраняются.
- После назначения другой франшизе нельзя применить чужой конфиг; дубли/старые ревизии безопасны; видно подтверждение применения и ошибки доставки.
- Продление даты отменяет старые напоминания; перезапуск worker не создаёт повторную рассылку.
- Ручное выключение прекращает новые операции, сохраняет историю и безопасно завершает перечисленные обязательства.
- Ошибка Frontpad видна у нужного филиала и в сводке франшизы, не исчезает через сутки и не вызывает общую Telegram-тревогу Bastion.
- Внедрение на действующий ресторан не меняет доступ неожиданно.

## Порядок работ и связи

1. Реестр функций и соответствие существующим permissions/операциям, идентичность франшизы и привязки установок.
2. Ручные наборы, дата оплаты, аудит и UI владельца Bastion.
3. Доставка конфигурации, подтверждения, локальная авторизация и полное скрытие недоступных функций.
4. Telegram-напоминания.
5. Ошибки филиалов/франшизы и отключение бизнес-тревог Bastion.
6. Сквозная проверка на действующей конфигурации, проверки каждого изменённого репозитория через `mix precommit` и соответствующие клиентские проверки.

Связанные задачи: [состояния интеграций и кухня](integration-status-and-kitchen-access.md), [сборка и развёртывание](deployment-reliability.md). Коммерческий допуск проверяется до отображения любых статусов интеграции. Новые сервисы онлайн-оплаты подписок, автоматические отключения и бэкапы изображений в эту работу не входят.
