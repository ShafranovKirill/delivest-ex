# Задача: исправление и рефакторинг состояний интеграций

Статус: к реализации.

Продолжение [состояний интеграций и доступа к кухне](integration-status-and-kitchen-access.md). Основание — ревью изменений `716fe72…f88cc2a` от 02.11.2026. Выборочные 99 тестов интеграций, кухни, выбора филиала и табло прошли; перечисленные ниже сценарии требуют отдельного покрытия. Полный набор тестов и браузерный E2E при ревью не запускались.

## Проблемы

1. После сохранения реквизитов формы обновляют `settings`/`crm`, но передают в `HealthComponent` прежний `current_branch`. `Presentation.state/2` читает реквизиты и использование из `branch.info`, поэтому блок состояния может показывать старые данные до перезагрузки. Например: сохранить токен и email Яндекс Доставки — форма сохранена, блок по-прежнему сообщает о незаполненных реквизитах. У CRM аналогично могут устаревать признаки отправки, источников и стоп-листа.
2. Миграция `20261102183731_add_warning_to_integration_health.exs` переводит старые строки `warning` в `ok`, сохраняя `checked_at`. Представление считает их успешной проверкой связи. Предупреждение само по себе не доказывает результат проверки; миграция создаёт ложный успех.
3. `HealthComponent` показывает кнопку проверки по одному `checkable?` и вызывает `Health.check/2` без проверки прав сотрудника. Страницы CRM и Яндекс Доставки доступны с `integrations.read`, поэтому сотрудник без права изменения может выполнять внешний запрос и сохранять результат проверки.

## 1. Единое актуальное состояние после сохранения

- Разделить редактируемую форму и сохранённое состояние: блок статуса строить только по успешно сохранённым данным.
- Выбрать один общий способ получения актуального контекста для `Presentation` и применять его на страницах провайдеров, в списке интеграций и маршрутах. Не исправлять отдельные поля вручную в каждом шаблоне и не создавать вторую копию бизнес-правил.
- После успешного сохранения обновлять необходимые данные филиала и сетевых настроек и явно обновлять компонент статуса. Учесть отслеживание изменений assigns у LiveComponent: изменение только формы не гарантирует повторный `update/2` компонента с прежними входами.
- Не выполнять лишнее чтение БД на каждый ввод символа. Неуспешная валидация/сохранение не должны подменять сохранённое состояние черновиком или сбрасывать предыдущую проверку связи.
- Проверить Frontpad, iiko, r_keeper, Яндекс Доставку, Яндекс Еду, ЮKassa, Zvonok, DaData и АТОЛ. Сетевые настройки и настройки филиала сохраняют свою область действия.
- Смена реквизитов после успешного сохранения сбрасывает актуальность проверки; сохранение прежних реквизитов или только переключателя не должно без причины терять результат связи.
- Сохранение неактивного провайдера не меняет активную CRM и маршрутизацию. Проверка связи не включает функции.

## 2. Безопасный перенос старых health-данных

- Для старой строки `status = warning` сохранить текст и время предупреждения отдельно, а результат связи считать неизвестным: `checked_at = NULL`. Внутреннее значение enum не должно превращать отсутствие результата в успешную проверку.
- Сохранить доказанные старые `ok`, `auth`, `failed` и их время. Новая схема должна независимо хранить предупреждение и результат связи, включая ошибку связи одновременно с предупреждением.
- До изменения миграций выяснить, применялась ли исходная миграция в развёрнутых средах. Если применялась, обеспечить отдельную корректирующую миграцию: изменение уже исполненного файла не исправляет существующую БД.
- После исходной миграции строка с предупреждением и `ok` может быть как преобразованной старой записью, так и записью с настоящим успехом. Не объявлять их различимыми без доказательств. При отсутствии надёжного признака выбрать консервативный сброс актуальности неоднозначных результатов, сохранить предупреждения и описать, каким интеграциям потребуется повторная проверка.
- Проверить чистое развёртывание, обновление со старой схемы и обновление после уже применённой исходной миграции. Для новой миграции использовать `mix ecto.gen.migration`.
- Проверить влияние сброса на `Yookassa.ready?/0` и другие потребители health: неизвестное состояние не разрешает действие, которому нужна подтверждённая готовность. Переключатели и ключи миграцией не менять.

## 3. Проверка подключения с авторизацией

- Зафиксировать общую политику: для филиальных интеграций нужны доступ к филиалу и `integrations.update`; для сетевых настроек — `admin`, как на соответствующих страницах. Учесть существующую семантику прав администратора.
- Сотрудник с одним `integrations.read` видит состояния без доступной кнопки проверки. Отдельно проверять права в серверном обработчике: скрытие кнопки не защищает от поддельного события.
- Вынести авторизованный запуск ручной проверки в общий вход, принимающий сотрудника, провайдера и область действия. Не копировать матрицу прав по LiveView. Проверка прав выполняется до внешнего запроса, записи health и журнала.
- Внутренние фоновые вызовы `report`, `warn`, `recovered` сохранить; им не нужно имитировать сотрудника. Просмотреть остальные входы ручной проверки, чтобы общий запрет нельзя было обойти соседней кнопкой.
- Для провайдера без настоящего API-запроса не предлагать проверку и не записывать успех по заполненности полей.

## Проверки приёмки

- LiveView: открыть настройки без реквизитов, успешно сохранить их, сразу увидеть актуальную полноту в блоке статуса без перехода или перезагрузки. Проверить минимум CRM и Яндекс Доставку, а также обновление сетевой интеграции.
- После смены ключа блок сразу показывает «Связь не проверена»; после проверки — результат для новых сохранённых реквизитов. Старый успех не возвращается при очередном рендере формы.
- Включение/выключение отправки и смена sources сразу отражаются в состоянии использования. Невалидная форма оставляет прежний сохранённый статус.
- Сохранение Frontpad при активной iiko сохраняет iiko активной и показывает правильные состояния обоих провайдеров.
- Миграционные фикстуры: старое предупреждение без доказанной проверки, успех без предупреждения, ошибка доступа, ошибка связи; отдельно — неоднозначные данные после первой миграции. Проверить сохранность текста и времени предупреждения и отсутствие выдуманного успеха.
- Проверить сохранение реальной ошибки связи при добавлении предупреждения, независимое снятие предупреждения и успешную повторную проверку.
- Сотрудник с `integrations.read` не видит кнопку; поддельное событие отклоняется. Assert: внешний HTTP не вызван, health не изменён. Проверить также чужой филиал и сетевой провайдер без `admin`.
- Сотрудник с допустимыми правами выполняет проверку в правильной области действия; результат виден в карточке, на странице провайдера и маршрутов.
- Добавить поведенческие регрессионные тесты в существующие наборы health/settings, `integration_live/*_test.exs` и необходимые проверки миграции. Не ограничиваться прямым вызовом `Presentation.connection/1`: ошибка обновления состояния воспроизводится через сохранение в LiveView.
- Выполнить `mix precommit`. Браузером проверить сохранение и обновление состояния без перезагрузки; использовать существующий E2E-контур при наличии подходящих фикстур. В отчёте указать реально выполненные проверки и ограничения.

## Границы

Не переписывать адаптеры внешних API, кухню, табло, подписки франшиз и жизненный цикл заказов. Сохранить три независимых факта: реквизиты, связь, использование. Изменения схемы и общего запуска проверки ограничить перечисленными дефектами. Обновить связанные задачи по фактическому завершению; прохождение прежних тестов само по себе не закрывает эту задачу.
