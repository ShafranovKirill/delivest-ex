# Исправить найденные сбои обновления и фоновой работы

Постановка после аудита `develop` от 2026-11-04. Выполнять части последовательно, каждую в отдельной ветке и с отдельным ревью по правилам репозитория. Приоритет внутри задачи указан ниже. Затрагиваются корневой Delivest, `agent/`, `server/` и `client/`. Для проверки доставки команд Bastion может потребоваться соседний `delivest-bastion`, но его изменение относится к [надёжности развёртывания](deployment-reliability.md).

## Цель и границы

Обновление установки сохраняет проверяемую точку отката при неудаче и повторе. Приложение не теряет планируемую отправку заказа на кухню и не перевыпускает токен из-за запоздалого ответа. Карусель подсказок не меняет активную карточку, пока пользователь держит на ней фокус.

Эта задача исправляет конкретные обнаруженные сценарии, включая проверку готовности после отката. Согласованные выпуски, хранение образов в GHCR, полная политика совместимости миграций и восстановление после рестарта Bastion остаются в [плане надёжности развёртывания](deployment-reliability.md). Для отката в пределах этой задачи требуется guard против известной несовместимости схемы. Более широкий механизм миграций разрабатывается отдельно.

## 1. P1. Зафиксировать состояние работающего выпуска до обновления

Текущий путь `agent/lib/delivest_agent/commands.ex` вызывает `Release.remember/1` перед `git pull`, затем подготавливает образы. `Release.remember/1` (`agent/lib/delivest_agent/release.ex`) сохраняет Git HEAD и ID работающих образов в `rollback.json`. Если pull обязательного образа закончился ошибкой, Git уже указывает на новую ревизию, контейнеры остаются прежними. Следующая команда обновления перезаписывает файл отката парой «новая ревизия, старые образы». При последующей ошибке запуска возврат может собрать несовместимую конфигурацию.

### Шаги


1. Определить состояние *текущего подтверждённо работающего выпуска*, *предыдущего выпуска для ручного отката* и *текущей попытки* как разные данные. Записывать их атомарно, чтобы прерывание записи и рестарт агента не оставляли частичный JSON. Сохранить чтение существующего `rollback.json` или предусмотреть явную миграцию старого формата.
2. Повтор неудавшейся подготовки должен использовать прежнюю точку работающего выпуска. После успешного запуска прежний подтверждённый выпуск становится предыдущим для ручного отката, а новый — текущим. Сохранённые образы прежнего выпуска остаются доступны для ручного отката. Пока новые контейнеры не стали рабочими, обе подтверждённые точки не перезаписываются.
3. Привязать сохранённые ID к конкретной установке. Сейчас `previous_ref/1` использует один тег `delivest-previous` на Docker-хосте, поэтому две установки с одинаковыми именами образов могут перезаписать тег друг друга. При восстановлении по тегу сверять его фактический ID с сохранённым `image.id`; для digest-reference проверять наличие точного digest, требуемого восстановленным Compose.
4. При сбое обязательного pull возвращать понятную ошибку без `compose up`. Решить отдельно, возвращать ли Git к прежней ревизии сразу или хранить незавершённую попытку. Реализация должна обеспечивать одинаковый результат при повторе и ручном откате.

### Приёмка

цепочка «неуспешный pull → повтор команды → неудачный запуск → автоматический откат» возвращает исходную Git-ревизию и исходные image ID. Одна установка не меняет точку отката другой. Повреждённое или неполное состояние выявляется до изменения работающих контейнеров.

## 2. P1. Считать состав сервисов после восстановления ревизии

`Commands.rollback/2` получает список сервисов до `git reset` и передаёт его в `Compose.up_prepared/2` после сброса. Если Compose изменился, в списке остаются удалённые имена или отсутствуют возвращённые сервисы.

### Шаги


1. После `git reset` перечитать определения Compose и получить список сервисов из восстановленной ревизии. Перед `up --pull never` проверить доступность всех необходимых точных image references и соответствие сохранённым ID.
2. Проверить сервисы, появившиеся, удалённые и переименованные между ревизиями, включая gateway и agent. Согласовать выбор сервисов для `gateway restart` с восстановленной конфигурацией.
3. Разделить в журнале исходную ошибку обновления, действия отката и результат проверки после отката. Перед автоматическим откатом применить guard против известной несовместимости схемы с предыдущим выпуском. Готовность восстановленного сайта и более широкая политика миграций описаны также в [плане развёртывания](deployment-reliability.md).

### Приёмка

ручной и автоматический откат выполняют Compose восстановленной ревизии. Ошибка отсутствующего сохранённого образа сообщается до пересоздания сервисов; успех отката подтверждён проверкой работающего сайта.

## 3. P1. Проверять обязательные хосты и фактически запущенный выпуск

`agent/lib/delivest_agent/config.ex` отбрасывает незаданные хосты, а `Status.checks/0` (`agent/lib/delivest_agent/status.ex`) проходит по оставшимся. Успешный ответ `/ready` содержит `version`, однако `Release.wait_healthy/1` принимает любой `ok`, не сверяя его с подготовленным выпуском.

### Шаги


1. Для установки определить обязательные API и витрину. Отсутствующий обязательный адрес возвращать как ошибку конфигурации, а не как пустой список проверок. При разных поддерживаемых конфигурациях явно указать, какие хосты обязательны.
2. Перед запуском сохранить идентификатор целевого образа или ревизии каждого приложения. После запуска сверить фактические контейнеры и ответы API/витрины с целью. Проверить поведение при старом контейнере, который всё ещё отвечает 200 и `status: ok`.
3. Повторить проверку после отката. Если старый код не совместим с уже применёнными миграциями, действовать по правилам [плана развёртывания](deployment-reliability.md), а не объявлять откат успешным по одному ответу HTTP.

### Приёмка

отсутствие обязательного хоста, 404, старая версия приложения и несоответствие image ID блокируют сообщение об успешном обновлении. Журнал называет не прошедшую проверку.

## 4. P2. Сохранить запланированную отправку заказа на кухню

В `server/lib/delivest/oms/kitchen.ex` функция `schedule_send/2` отменяет старое задание, не проверяет результат `Oban.insert/1` и возвращает `{:ok, order}`. Отказ вставки оставляет заказ без новой задачи до резервного сканирования.

### Шаги


1. Перепланирование сделать атомарным относительно отмены прежнего задания или обеспечить восстановление прежнего задания при ошибке. Обрабатывать `{:ok, job}` и `{:error, reason}` вместо безусловного успеха.
2. Проследить результат через `order_accepted/1`, `send_due/1` и `reschedule_branch/1`. Сейчас `Kitchen.OrderSubscriber.plan/1` игнорирует ответ `order_accepted/1` и всегда возвращает `:ok`, а `DispatchWorker.perform/1` также возвращает `:ok` после резервного сканирования. Ошибка должна доходить до outbox/Oban и сохраняться в диагностике. Разобрать частичные ошибки при перепланировании филиала, чтобы один неудачный заказ не маскировался успехом остальных.
3. Не отправлять заказ в кухню дважды при повторной обработке события или одновременной работе воркера и резервного прохода. Резервный проход сейчас запускается каждые пять минут.
4. Проверить изменение `cook_by`, отключение кухни, смену CRM и завершение/отмену заказа, пока задача запланирована.
5. Тем же правилом обработки результата закрыть смежный конкретный путь уведомления клиента. `Push.notify_items_removed/2` игнорирует ответ `Oban.insert`, а `Push.OrderSubscriber` отдаёт `:ok` в outbox. При отказе вставки сохранить ошибку для повтора, не отмечать событие доставленным и не создать повторное уведомление при повторной доставке события.

### Приёмка

при искусственном отказе Oban сохраняется действующая старая задача либо возвращается явная ошибка, которая доходит до обработчика события и запускает повтор по предусмотренному механизму. В обычном случае задача исполняется один раз в рассчитанный срок; резервный проход остаётся рабочим и сообщает о частичном отказе. Событие удаления позиции не считается доставленным, если уведомление не поставлено в очередь.

## 5. P2. Обновлять токен только после проверки его поколения

`server/lib/delivest/integrations/token_cache.ex` сериализует выпуск на cache miss через `Cachex.fetch`, но `run/4` при ответе 401 вызывает `refresh/2`, который безусловно удаляет ключ. Запоздалый 401 для старого токена может удалить уже выданный новый токен.

### Шаги


1. Передать в refresh отклонённый токен. Если значение по ключу уже другое, использовать его без повторного выпуска. Если значение прежнее, заменить его под сериализацией по этому ключу.
2. Сохранить TTL, невключение ошибок выпуска в кеш и существующее поведение при повторном 401. Проверить, что повторный вызов использует новое значение ровно один раз.

### Приёмка

при двух параллельных запросах и позднем 401 новый токен остаётся в кеше, выпуск не дублируется, оба вызова получают корректный итог.

## 6. P2. Останавливать карусель на время взаимодействия

В `client/src/modules/cart/components/CartPromotionHints.vue` наведение и фокус управляют одним `paused`. `onMouseLeave` снимает паузу, даже когда кнопка карусели остаётся в фокусе.

### Шаги


1. Отдельно отслеживать указатель и фокус внутри карточки. Включать таймер лишь когда оба состояния неактивны. Сохранить ручное переключение, жесты, круговой порядок и настройку уменьшения движения.
2. Проверить смену списка подсказок во время паузы и после ухода фокуса, чтобы не появлялись лишние интервалы.

### Приёмка

карточка не переключается автоматически при фокусе, наведении и их пересечении. После ухода указателя и фокуса листание возобновляется один раз.

## 7. P2. Закрыть обнаруженный пробел мобильного редактирования заказа

В `server/lib/delivest_web/live/staff/order_live/order_form.ex` действие «Нет в наличии» передаётся только в `CartComponent.render_items` внутри контейнера `hidden lg:block`. На узком экране показывается `CatalogComponent`, где соответствующего действия нет.

При правке заказа дать сотруднику на ширине 320–390 px тот же способ отметить позицию недоступной. После сохранения проверить удаление позиции, пересчёт суммы и уведомление клиента. Сохранить действующее поведение десктопа и разграничение прав.

## Неподтверждённые сценарии, требующие воспроизведения

- Проверить сохранение черновика оформления при обязательном входе и смене `cartId` после авторизации. `OrderForm.vue` восстанавливает `checkout-draft` только при совпадении сохранённого `cartId` с текущим. Сам факт смены ID в действующем потоке входа пока не подтверждён, поэтому сначала записать фактический сценарий и только затем менять поведение.
- `Crm.SyncWorker` фиксирует успешный и авторизационный исход в `Integrations.Health`, но временную ошибку провайдера в статус `:failed` не переводит. Проверить ожидание из [задачи OTP](otp-usage.md), где обещана защита от лежащего провайдера. Если нужна автоматическая защита, определить безопасную классификацию и TTL временных отказов, в том числе для запросов Frontpad с неоднозначным исходом. Не повторять такие запросы без правил идемпотентности.

Отдельно подтвердить на реальном Docker Compose и registry сценарии загрузки, повтора и отката. Проверка образов GHCR и production требует доступной среды. Физический телевизор и внешние провайдеры имеют собственные задачи [экрана выдачи](pickup-board.md) и [проверки API](api-testing.md); их результаты не выводятся из локальных тестов этой задачи.
