# Задача: АТОЛ Онлайн — потерянный ответ, повтор чека, состояние кассы

Адаптер АТОЛ сделан по документации v5, покрыт заглушками (`testonline.atol.ru` с dev-машины не отвечает, контрактный тест `--only atol_contract` ждёт доступа). Сверка кода с README и `docs/api-v5.txt` показала: ситуация «ответ на регистрацию потерян» обработана неверно, и чек, который АТОЛ уже принял, мы помечаем как провалившийся.

Основа: [fiscal-receipts.md](fiscal-receipts.md) и `integrations/atol_online/README.md`.

## 1. Ошибка 33 (готово)

`AtolOnline.classify_error/1`: коды 13, 32, 42 постоянные, 1 и 50 повторяются, 56 — отложить, остальные `{:atol, _code, _text}` — постоянные. Код 33 попадает в последнюю ветку.

README (раздел «Идемпотентность» и таблица ошибок) говорит другое: 33 — «чек уже есть, не дубль. Ждать результат», тип `System/Wait` в `api-v5.txt`. Сценарий: регистрация ушла, ответ потерялся, `RegisterWorker` повторил с тем же `external_id`, получил 33, `classify_error` вернул `:permanent`, `Fiscal.failed/3` поставил чек в `fail`. В АТОЛ чек при этом пробивается, клиент его получает, а в нашей базе он помечен как не пробитый.

- Ветка `{:atol, 33, _}` в `classify_error/1` отдельная: чек не ошибка, а ожидание результата.
- `Api.handle/1` сохраняет `uuid` из тела ошибки 33, если АТОЛ его отдаёт (README: «проверить на тестовой среде»). С `uuid` регистрация возвращает `{:ok, %{uuid: uuid, status: :wait}}` и дальше работает опрос `report`.
- Без `uuid` — п.2.
- Тесты: 33 с `uuid` переводит чек в `wait` и запускает опрос; 33 без `uuid` не ставит `fail`.

## 2. Чек без `uuid` (готово)

`Fiscal.handle_callback/3` ищет чек только по `uuid` (`Repo.get_by(Receipt, uuid: uuid)`), `AtolOnline.fetch/2` без `uuid` возвращает постоянную ошибку `:no_uuid`. Если ответ на регистрацию потерян, `uuid` у нас пуст, а callback от АТОЛ приходит с `uuid` и `external_id`.

- `parse_callback/1` возвращает ещё и `external_id`. `Fiscal.handle_callback/3` ищет чек по `uuid`, при промахе по `id` равному `external_id` (наш `external_id` — `receipt.id`) и заполняет `uuid` из callback.
- `RegisterWorker` после 33 без `uuid` ставит чек в `wait` и планирует `PollWorker`. Если callback за 300 с не пришёл, а `uuid` неизвестен, чек уходит в тревогу «Проверьте чек в личном кабинете АТОЛ» с `external_id`, а не в `fail`.
- Что делает АТОЛ в таком случае (отдаёт ли `uuid` в 33, приходит ли callback при повторе) — проверить на тестовой среде и закрепить в контрактном тесте.
- Тесты: callback без совпадения по `uuid`, но с `external_id` чека находит чек и сохраняет `uuid`; чужой `external_id` не находит.

## 3. Таймаут очереди (готово)

README: чек 300 с в очереди — `fail`, `error.type: timeout`, «чек не пробит, повторить с новым `external_id`». В коде `status: fail` всегда конечный (`Fiscal.apply_result/3`).

- Различать `fail` по таймауту (чек точно не пробит) и остальные `fail`.
- Повтор с новым `external_id`: `Payload.build/4` получает `external_id` с номером попытки (`"<receipt_id>-2"`), хранится в поле чека. Максимум 3 повтора, дальше тревога.
- Остальные `fail` (ошибки ККТ, раздел 7.2 `api-v5.txt`) в тревогу оператору: часть из них требует действия на кассе (смена, ФН).
- Тесты: `fail` с `type: timeout` порождает новую регистрацию с другим `external_id`; `fail` типа `driver` не повторяется.

## 4. Состояние кассы и ФН (готово)

`AtolOnline.health_check/1` только получает токен. Документ «API сервиса получения информации о ККТ и ФН» (`docs/kkt-info-api.txt`) отдаёт по группе касс состояние: онлайн, смена, заполненность ФН, срок замены ФН, ошибки. Сейчас о заполненном ФН узнаём по ошибкам регистрации.

- `AtolOnline.Api.kkt_info/1` (группа касс из настроек) и разбор ответа по документу.
- `health_check/1` дополнительно: касса не на связи, ФН заполнен более чем на 90 процентов, срок ФН меньше 30 дней, неотправленные в ОФД документы старше часа дают предупреждение в `Health` на странице интеграции и тревогу администратору.
- Проверка раз в час поллером по образцу `Integrations.Poller`.
- Смена: сервис не отдаёт время открытия смены, условие «открыта более 24 часов» не проверяется. Касса не на связи — `networkErrorCode` больше нуля или неотправленные документы старше часа. Боевая среда только: для песочницы проверка отключена.
- Предупреждение видно на карточке «Чеки» и в странице настроек чеков.
- Тесты: каждое условие даёт предупреждение; исправная касса его снимает.

## 5. Чеки коррекции

`Receipt.kinds` включает `:sell_correction`, `Payload` и README описывают `correction_info`, но запустить коррекцию из админки нельзя. Если чек не пробился (п.3, 4), исправлять приходится у АТОЛ вручную.

- Действие «Пробить коррекцию» в карточке чека: `sell_correction` с `correction_info.type: self`, `base_date` и `base_number` исходного чека.
- Доступно только администратору и только для чека в `fail` и после подтверждения.
- Тесты: коррекция создаёт новый чек с видом `sell_correction`; без права не доступна.

## Что не делаем

- **Маркировка** (`mark_code`, `payment_object: 33`): продаём блюда собственного производства.
- **Расход** (`buy`, `buy_refund`): не нужен.
- **ТС ПИоТ** и разрешительный режим: нет документа и касс.

## Что нужно от АТОЛ

Тестовый доступ (`testonline.atol.ru` не открывается с dev-машины, нужен другой канал), логин, пароль и код группы. Нужно подтвердить: ответ ошибки 33 (отдаёт ли `uuid`), поведение callback при повторе, формат ответа KKT-info.
