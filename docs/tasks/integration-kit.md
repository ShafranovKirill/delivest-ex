# Задача: общий набор для интеграций

Интеграций будет много: Frontpad, iiko, r_keeper, Яндекс Еда и Delivery Club, Яндекс Доставка, АТОЛ, ЮKassa. Сейчас каждая повторяет одно и то же по-своему: свой журнал запросов (`YandexEdaJournal`, журнал Яндекс Доставки), свой токен, свой опрос. Общие части выносятся один раз, до iiko и касс.

## Что выносится

| Часть | Сейчас | Нужно |
|---|---|---|
| Журнал запросов | У Яндекс Еды и Яндекс Доставки свои | Одна таблица `integration_requests`: провайдер, филиал, направление (к нам / от нас), метод, статус, длительность, тело с маскировкой секретов, связь с заказом. Срок хранения как у технических логов. Страница журнала в админке — общий компонент |
| Токены | У каждого своё | `Integrations.TokenCache`: ключ (провайдер + аккаунт), получение, срок жизни, обновление заранее и на ошибке «токен истёк». АТОЛ — 24 ч, iiko — 1 ч, Яндекс Еда — свой OAuth |
| Входящие вебхуки | Обрабатываются сразу в контроллере | Inbox, см. [order-events.md](order-events.md): запись с уникальностью `(провайдер, id события)`, ответ 200, обработка задачей |
| Опрос | `PollWorker` Яндекс Доставки, `StopSyncWorker` CRM | `Integrations.Poller`: что опрашивать (активные заказы провайдера, стоп-лист), интервал, остановка на финальном статусе. r_keeper — статусы, АТОЛ — чеки без callback, ЮKassa — зависшие платежи |
| Проверка связи | Своя кнопка у каждого | Колбэк `health_check/1` у провайдера, единая кнопка «Проверить подключение» и статус на карточке интеграции |
| Ошибки | `classify_error/1` у CRM | Тот же контракт для всех провайдеров: `:permanent`, `:retry`, `{:snooze, сек}`, `:auth` (тревога «переподключите») |
| Контрактные тесты | `:yandex_contract` | Тег на провайдера (`:atol_contract`, `:iiko_contract`, `:rkeeper_contract`), `make contract P=atol`, тестовые доступы в `.env` контрактов, не в CI |

## Правила для любой интеграции

- Все HTTP — через `Delivest.HTTP.Client` и журнал.
- Каждый исходящий запрос, меняющий данные, — с ключом идемпотентности, если провайдер его поддерживает (iiko `order.id`, ЮKassa `Idempotence-Key`, АТОЛ `external_id`).
- Вебхук — только сигнал: по нему перечитываем объект у провайдера.
- Изменение, пришедшее от провайдера, не отправляется обратно этому же провайдеру, см. [order-events.md](order-events.md).
- Секреты в настройках — `redact: true`, в журнале — маска.
- У каждого провайдера `README.md` с доступом, тестовой средой, таблицами полей и статусов, `docs/` с исходной документацией.

## Порядок

После [событий и outbox](order-events.md): inbox и опрос опираются на них. Существующие Яндекс Еда, Яндекс Доставка и Frontpad переводятся на общий журнал и токены.

## Сделано

Описание и как пользоваться — в [README интеграций](../../lib/delivest/integrations/README.md#общий-набор).

- `integration_requests` и `Journal`: исходящие через `Client` с `journal:`, входящие через plug `IntegrationJournal`. Подключены Frontpad, Яндекс Еда, Яндекс Доставка, Zvonok. `YandexEdaJournal` удалён. Вкладка или блок «Журнал запросов» на их страницах.
- `TokenCache`: push API Яндекс Еды.
- `Inbox`: вебхук статусов Frontpad. Яндекс Еда — наш API, а не вебхуки, Яндекс Доставка — опрос.
- `Poller`: `PollWorker`, `JournalWorker` Яндекс Доставки и `Crm.StopSyncWorker` заменены.
- `Error` с `:auth`, `Health` с `health_check/1` у Frontpad, Яндекс Еды и Яндекс Доставки.
- Контрактные тесты: `:yandex_contract` → `:yandex_eda_contract`, общий `:contract` исключён в `test_helper.exs`, `make contract P=...`.

Не сделано: DaData в журнал не пишется (запрос на каждую букву адреса), Zvonok обрабатывает вебхук сразу.
