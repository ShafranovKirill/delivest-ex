# F04: Яндекс Директ и Метрика

Дата: **17 ноября 2026**. Реализация в `codex/yandex-direct-metrika`; сохраняется локальными коммитами. Push, PR, merge в develop/main и production не выполняются.

## Решения владельца

- Только основной Delivest; лендинг не меняется.
- В админке разрешены необходимые настройки и диагностика. Новые клиентские окна без согласования запрещены.
- После явного включения администратором и подтверждения настройки политики сбор начинается с открытия меню. Вебвизор выключен.
- Действующие юридические документы автоматически не публикуются и не заменяются.

## Реализовано

- Общий HTTP-клиент: opt-in `response: :full`, статусы 200/201/202, безопасные URL/формы/исключения, сохранение поведения остальных интеграций.
- Настройки сети/филиалов, независимые выключатели посещений, конверсий, ecommerce, фида и расходов, права функций платформы. По умолчанию всё выключено.
- Токены AES-256-GCM с отдельным постоянным ключом `YANDEX_ADS_ENCRYPTION_KEY`. При потере ключа отправка останавливается; реквизиты не перезаписываются запасным ключом.
- OAuth connect/callback с одноразовым состоянием и сроком действия, обновление доступа, ручные отдельные токены. Проверки кабинета, выбранного счётчика и цели. Создание цели и регистрация фида по явным действиям администратора.
- Метрика использует события существующей воронки. F04 и Яндекс независимы. Только очищенные публичные URL без телефонов, адресов и ID заказов. Смена пользователя/филиала/подключения/версии функций очищает буфер. Конфигурация проверяется каждые 20 секунд; сервер проверяет текущие разрешения при записи.
- Detail/add/remove используют UUID предложения и подтверждённое изменение корзины. Браузер не отправляет purchase. Перед заказом ожидание сохранения идентификатора ограничено 200 мс; аналитика не запрещает checkout.
- Отдельное чтение товара `/client/branches/:branch_id/products/:product_key` по UUID/slug. Общий с меню публичный DTO, промо, стопы, модификаторы и награды. Чтение ограничено товаром и зависимостями.
- Прямые товарные/категорийные ссылки, совместимость `?product=slug|UUID`, состояния существующей карточки. HTTP 404 сохраняет SPA для показа недоступного товара внутри меню.
- Одинаковые серверное содержимое и метаданные для посетителей и роботов. Sitemap с порциями товаров по 1000. Фид `/catalog/:branchSlug.xml` строится партиями по 200 с едиными offer ID, ценой и доступностью.
- Идентификаторы Яндекса отделены от доверенной атрибуции F04. Владелец определяется сервером; первая достоверная атрибуция клиента не переписывается.
- Транзакционный снимок completed в OMS, включая наличные. Отдельное Oban-задание для сети. Повтор и повторное завершение не создают вторую продажу. Неизвестный исход не отправляется вслепую заново; известную загрузку можно сверить по ID из админки.
- Офлайн-цель и MP purchase имеют отдельные состояния. Принятие запроса не доказывает запись события или привязку. Откат завершения после отправки остаётся видимым расхождением.
- Расходы один раз на кабинет/период, очередь Reports и `retryIn`. Атомарная замена полного среза, включая исчезнувшие строки. Проверки валюты/часового пояса. Переподключение кабинета не смешивает аккаунты.
- Рекламный отчёт переиспользует опубликованные итоги F04 и показывает полноту/свежесть. Расходы и проблемы передачи доступны только с правами сети и доступом ко всем филиалам.
- Связи доверенных ссылок Delivest с импортированными кампаниями. ROAS/CPA только по опубликованным F04 и полному импорту расходов. Текущая связь применяется к истории ссылки; это явно показано. Неполнота не превращается в ноль или доказанный прирост продаж.
- Ограниченная очистка сырых идентификаторов через 90 суток и расходов через 36 месяцев, независимо от выключения внешнего обмена.

## Первое подключение

1. Задать постоянный ключ `YANDEX_ADS_ENCRYPTION_KEY`; генерация: `openssl rand -base64 32`. Сохранить его отдельно от резервной копии БД вместе с эксплуатационными секретами.
2. Для OAuth: `YANDEX_ADS_OAUTH_CLIENT_ID`, `YANDEX_ADS_OAUTH_CLIENT_SECRET`, `YANDEX_ADS_OAUTH_REDIRECT_URI`. Callback: `/staff/integrations/yandex-ads/callback`. Допустим ручной ввод токенов.
3. Проверить одобрение API Директа и права счётчика. В «Интеграции → Яндекс Директ и Метрика» подключить кабинет, выбрать счётчик/филиалы/потоки, выдать функции платформы.
4. Проверить политику, подтвердить основание сбора в настройках. OAuth и включение зависимостей сами по себе не запускают сбор.
5. Проверить подключения, найти/создать completed-цель. Для purchase отдельно настроить Measurement Protocol. Не выбирать две финансовые цели оптимизации одного заказа.
   Кнопка «Настроить цели меню и оформления» создаёт только отсутствующие вспомогательные цели воронки. Она не создаёт вторую финансовую цель и не запускает кампании.
6. Проверить публичный фид и зарегистрировать его. Кампании, география, ставки, бюджеты и запуск рекламы управляются в Директе.
7. Импортировать расходы и связать доверенные ссылки с кампаниями. Проверить покрытие F04 за тот же период.

## Внешняя приёмка остаётся отдельной

Локальные тесты и синтетические ответы не подтверждают доступ к реальному кабинету, модерацию фида, индексацию, привязку конверсии или production capacity. Перед включением проверить разрешённый путь: клик → карточка → корзина → наличный заказ → completed → загрузка → обработка → расход. Затем общую кампанию на двух филиалах, частичный возврат, откат завершения, повторный импорт и отказ Яндекса при работающем checkout.

MP не гарантирует позднюю привязку. Нет подходящего ClientID — нет выдуманной покупки. Неизвестная загрузка требует сверки. Пропущенные периоды выключенного сбора не восстанавливаются. Изменения расходов старше автоматического скользящего окна требуют повторного импорта нужного периода. Нагрузочные пороги определяются по реальному пилоту.

Фактические результаты локальных проверок: [итоговая приёмка](acceptance.md). Полный root preflight/E2E и push — только по отдельной команде «Пуш в Девелоп»; адресные браузерные проверки разрешены.
