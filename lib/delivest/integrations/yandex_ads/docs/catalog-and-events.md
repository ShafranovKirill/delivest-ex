Описание внешнего формата сверено с [YML](https://yandex.ru/support/direct/ru/feeds/requirements-yml), [Feeds API](https://yandex.ru/dev/direct/doc/ru/feeds/feeds), [ecommerce Метрики](https://yandex.ru/support/metrica/ru/data/e-commerce).

## Каталог и идентификатор предложения

YML-фид должен следовать требованиям Direct к структуре каталога и ценам. [Синтетический YML](examples/catalog.xml) показывает форму данных. До реализации выбрать стабильный `offer id`: то же значение использовать в фиде, `pr1id`/ecommerce data layer и серверном соответствии заказанного товара. Каталог строить через общий public-offer builder и single-product API с branch scope; прямые ссылки на товар/категорию должны поддерживать `?product=slug` и `?product=UUID` и SEO. Проверить варианты модификаторов, отсутствующих товаров, скрытых предложений, цены со скидкой и валюты на реальном тестовом фиде. Feeds API для `get`, `add`, `update`, `delete` документирован на `/json/v501/feeds`; этот подготовительный пакет не выполняет запись, регистрация фида — будущий этап. Управление бюджетами и запуск кампаний вне F04. [Требования YML](https://yandex.ru/support/direct/ru/feeds/requirements-yml), [Feeds API](https://yandex.ru/dev/direct/doc/ru/feeds/feeds).

В ссылках рекламы Direct допускает URL-макросы и UTM. `yclid`, UTM и реферер — входные внешние параметры; сохранить оригинал как данные, нормализовать и валидировать отдельно. Неизменяемый первый источник пользователя и атрибуция заказа — разные величины: для заказа сервер выбирает последний достоверный переход за семь суток. Перед запуском проверить редиректы, 404/410 landing и сохранение меток до клиентского события. [URL-макросы и метки](https://yandex.ru/support/direct/ru/statistics/url-tags), [контекст F04](https://app.notion.com/p/41b31ec95e448171a833ee7fa73547bc).

## Клиент и сервер

В браузере счетчик получает `ClientID` через `getClientID`, фиксирует согласованную цель через `reachGoal`, ecommerce события `detail`, `add`, `remove` — через data layer. [Синтетический JS](examples/browser-events.js) показывает эти вызовы без встраивания в bundle. Для SPA с `defer: true` нужна явная отправка виртуальных просмотров `hit` при смене маршрута; отключение счетчика в новой версии кода — `ym(counterId, 'destruct')`. Поведение проверить с выбранной настройкой счетчика в пилоте. Событие `purchase` и финальную цель `completed` формировать только по подтвержденному сервером завершению заказа, включая наличную оплату, а не при открытии страницы «спасибо». Использовать существующие receipts/attribution, а не второй механизм учета. [Код счетчика SPA](https://yandex.ru/support/metrica/ru/code/counter-spa-setup), [JS API](https://yandex.ru/support/metrica/ru/objects/method-reference), [ecommerce](https://yandex.ru/support/metrica/ru/data/e-commerce).

Для отложенного `completed` первичный путь — офлайн-конверсия с сохраненным разрешенным `ClientId`/другим идентификатором. MP может добавлять своевременные события в визит, но его окно ограничено. При повторе заказа/переподключении destination нужен явный ключ отправки; при недоступном идентификаторе визита не синтезировать историю посещений. [Офлайн-конверсии](https://yandex.ru/dev/metrika/ru/management/offline-conv), [MP](https://yandex.ru/dev/metrika/ru/data-import/measurement-about).
